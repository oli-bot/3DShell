## 一、已修复（本轮改完并验证）

### 1. `ai_modal.c` 绕过渲染包装层 —— 模块无法上宿主机测试

**问题.** 全项目底部屏幕的绘制都走 `renderer_draw_*` 包装（`softkb.c`、
`project_ui.c`），唯独 `ai_modal.c` 直接调 `C2D_DrawRectSolid`，还手工重复了
4 遍 `0xRRGGBBAA → C2D_Color32` 的字节重排：

```c
C2D_DrawRectSolid(0, 0, 0.55f, 320, 240, C2D_Color32(
    (col >> 24) & 0xff, (col >> 16) & 0xff,
    (col >>  8) & 0xff,  col        & 0xff));
```

后果有两个，是同一个根因：
- **无法宿主机测试.** 用了 `C2D_` 符号，就不能像 `project_ui.c` 那样对着
  `tools/stub/citro2d.h` 编译，所以这个 548 行的模块是全项目唯一没有测试的
  纯逻辑模块（淡入淡出状态机、Markdown 变换、软换行、省略号）。
- **无法跟随主题.** 手工重排颜色意味着颜色是写死的。

顺带一提，同一个文件里的**文本**是走包装的（`renderer_draw_text_px_z`，
`renderer.h:93-95` 的注释还专门说明了这一点），只有矩形走直连——文件内部
自相矛盾。

**修复.** 5 处矩形全部改走 `renderer_draw_rect_px`，删掉 4 处字节重排。
`renderer_draw_rect_px` 的实现就是 `C2D_DrawRectSolid(px, py, z, w, h,
rgba_to_c2d(rgba))`，而 `rgba_to_c2d` 正是那段被删掉的字节重排，因此**逐字节
等价**，画面不变。

**验证.** 新增 `tools/test_ai_modal.c` + `tools/test_ai_modal.sh` +
`make test-ai-modal`，**50 项断言全过**。测试直接钉住了这次改动：断言 7 个
矩形的数量、位置与颜色（外遮罩 / 模态底 / 四条边框 / 分隔线），并用
颜色帧缓冲验证淡入中途的 alpha 精确等于模块自己承诺的 192 / 114，以及
Markdown 变换（`#`、`- `、`**`、`` ` ``、`[t](u)`、围栏）、问题行省略号、
答案区截断。

> 测试写出来先抓到了我自己的一处误解：`ai_modal_open()` 会重置淡入动画，
> 所以紧接着 `draw()` 那一帧 alpha 为 0、什么都不画。断言正确，是我的测试
> 写错了——已修正测试。

### 2. `main.c` 残留的“状态栏”机制 —— 12 处写入、0 处读取

`status_buf[80]` 与 `status_color` 在 12 个地方被赋值，只在原来的 1552 行
被 `(void)` 掉：

```c
(void)status_buf; (void)status_color;  /* not currently rendered */
```

`COLOR_OK / COLOR_WARN / COLOR_ERR` 三个宏（原 66-68 行）只为喂这个没人看的
变量而存在，并且 `reconnect_ssh()` / `keychain_bootstrap()` 各带一个
`status_buf` / `status_color` 参数，唯一用途就是往里写。

关键是**真正的反馈另有其路**：每一处 `status_buf` 写入旁边都有一条
`terminal_write()` 把同样的话直接写进终端（`SSH error: …`、
`Tailscale error rc=…` 等），用户看到的其实是它。所以这是纯粹的死重，
而且会误导读者以为错误有专门的状态显示。

**修复.** 删掉缓冲区、颜色变量、三个宏，以及两个函数上的死参数。
`config_load()` 的返回值原本只用来拼那句没人看的话，改为显式
`(void)` 并加注释说明失败会由连接阶段在终端里报出来。

### 3. `ai_modal.c` 的 `MAX_ANSWER_LINES` 常量名不副实

声明为 14 行，但代码从不使用——答案区的行数预算其实是几何算出来的
（从 y=32 起每行 13 px，越过 `ANSWER_BOTTOM` 就截断）。常量留着会让读者
以为改它就能改行数。已删除，并在文件头注释里写明预算是几何的、
没有需要同步的旋钮。

## 三、死代码 / 潜在问题（已定位，未改）

**L1. `KIND_PAGE_TOGGLE` 是死枚举。** `softkb.c:157` 声明时注释就写着
“unused by new layouts”，但 `:1931`、`:1956-1959`、`:1990`、`:2357` 共 4 处
仍在为它分支——而没有任何一个键声明为这个 kind。属于无害的防御性死代码，
删它要动 6 个位置却不改变任何行为，所以留着等你决定。

**L2. 一批未被引用的宏（约 16 个）。** 其中最值得注意的是
`terminal.h:4,8` 的 `TERM_MAX_COLS 80` / `TERM_MAX_ROWS 48`：名字和注释
（“Maximum terminal height…”）都像被强制的上界，但代码里**从未使用**。
真正的网格尺寸是 `terminal_init(cols, rows)` 里 `calloc(cols * rows, …)`
按渲染器给的尺寸动态分配的（`terminal.c:92`），所以这两个宏既不设限也不
校验——读者很容易误以为越界会被挡住。其余如 `R_BOT_ROWS`、
`ROW_X_0/1/3`、`STATUS_Y`、`BOTTOM_ROW_Y`、`KW`/`KS`/`KP`（已被 `KEYAT`
取代）、`N_CHAR`、`SCR_H`、`BODY_Y1`、`HIT_IS_TAB`、`L_EN` 均为残留。

**L3. 两条保存路径的数据丢失语义不一致。**
- 设置页保存前会**重新读取文件再覆盖导出**，以保住用户在 SD 卡上手工做的
  改动（`main.c:1805-1807`，注释写明用意）。
- 项目卡片页直接整份写回内存中的 `g_loaded_settings`（`main.c:1707`），
  没有那层重读。

于是：应用运行期间在 SD 卡上手工改过 `settings.ini`，再从项目页改一张卡片，
那次手工改动会被覆盖；从设置页改则不会。是否统一，取决于你想要哪种语义。

## 七、第二轮深挖：跨模块缺陷类（已修复并验证）

第一节到第三节扫的是“结构 / 文档”类问题。这一轮换了三个**新的缺陷类**，每条
都先在代码里复现过才动手：

| 缺陷类 | 扫的对象 | 命中 |
|---|---|---|
| 不可信输入的边界安全 | ANSI 解析器、CSI 参数、光标回存 | 5 类堆越界（T1） |
| 资源生命周期 / 错误路径 | SSH slot 状态机、aux channel 归属 | 1 处 slot 卡死（T2）+ 2 处 UAF（T3） |
| 状态机与时序 | 淡入淡出、输入门闸、无进展重试 | 3 处（T5 / T6 / T7） |
| 不可信输入的工作量（非越界） | SU/SD 重复次数、各重复类操作 | 1 处无界循环（T8） |

> T8 是 T1 修完之后的**复查**里自己找到的：修 T1 时给参数加了
> `TERM_PARAM_MAX 9999` 上界，于是回头核了一遍「值有了上界，工作量是否也
> 有」，结果 `S`/`T` 是唯一漏网的。**加值上界不等于加上工作量上界**——
> 这是一个独立的缺陷类，值得单独扫一遍。

### T1. `terminal.c` ANSI 解析器：5 类堆越界

远程主机（或任何往 pty 写字节的东西）发来的序列是**不可信输入**，而解析器
把它们直接当索引用。

- **根因只有一处**：CSI 收集区间是 `0x20-0x3f`（`terminal.c:739`），而 `-`（0x2d）
  落在这个区间里，所以 `ESC[-5B` 会把 `-5` 交给 `strtol`。此后
  `put_char` 用负的 `cur_y` 算 `cells[cur_y*cols+cur_x]` 写到缓冲区之前；
  `ESC[38;5;-5m` 读 `theme_palettes[th][-5]`；`P`/`@`/`L`/`M`/`r` 的
  `memmove` 长度都能变负。
- **修法**：在**参数解析点**加一次钳位，而不是去逐个审二十来个消费者。
  新增 `TERM_PARAM_MAX 9999`（与 xterm 自己的上界一致），
  `if (v < 0) v = 0; if (v > TERM_PARAM_MAX) v = TERM_PARAM_MAX;`。
  非负参数一到位，所有消费者的比较就都成立了，`S/T/L/M` 的重复计数也顺带被限住。
- `DECSTBM`（`ESC[r`）另外补了**两端钳位 + 顺序检查**：`top > bottom` 时
  按 xterm 语义整条忽略，保留原边距。
- `L`/`M` 补了 `cur_y > bot`（无效果）与 `cur_y == bot`（该行被推出区域，
  应**清空**）两个分支。原来的代码在 `cur_y == bot` 上做的是 0 长度 `memmove`
  加一次清行，即“被挤出区域的那行消失”——这是**正确**行为，所以新代码是
  显式复现这个清空，而不是简单 `break`（那样才是行为回归）。
- **我自己额外找到的第 6 类**：`terminal_resize` 钳了 `cur_x/cur_y`
  （`:192-193`）但**没钳 `saved_x/saved_y`**，而五处恢复点
  （`:631,687,694,769`）都是直接写回。于是：40 行双屏网格里 `ESC 7` 存光标
  → `START+L` 退回 20 行 → `ESC 8` 把 `cur_y=39` 恢复到 20 行网格 →
  下一次 `put_char` 写到分配区外约 19 行。修在 `terminal_resize` 一处，
  覆盖全部五个恢复点。

**验证（这是最硬的一条）**：把 `source/terminal.c` 用 `git stash` 退回 HEAD，
在 ASan+UBSan 下重跑，得到

```
FAIL: a negative CSI parameter must leave the cursor in the grid
==74103==ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 4 at 0x613000000020 thread T0
    #0 put_char+0xa08
0x613000000020 is located 32 bytes before 384-byte region
```

正是预测的负索引；`git stash pop` 后转绿。

### T2. `ssh_client.c`：`step` 被两个状态机共用，关窗可能卡死

每个 slot 只有一个 `step` 字段，**开**机器和**关**机器共用它。
`ssh_open_shell` 在 pty 成功、shell 还没成功时会把它停在 3（`:603`→`:605`）。
此时若用户关掉这个窗口（或会话掉线），`ssh_close_slot` 里
`while (s->step < 3)` 直接不成立，**不释放 channel 就返回成功**，
slot 永久停在 `SSH_SLOT_CLOSING`，此后被 `ssh_open_shell` 一直拒绝。

正常关闭不受影响，因为成功路径会把 `step` 归零（`:615`）——但 3 是真实可达的
中间态。修法：`if (s->step > 2) s->step = 0;`（0..2 属于开机器，只回退更大的值）。

### T3. `main.c`：两处 aux channel 释放后使用（UAF）

`ssh_disconnect` 会释放每个 slot 的 channel 并 `free(ssh)`（`:404-427`），
但**完全不碰 aux channel**——`ssh_aux_channel_t` 对 `ssh_client_t` 是不透明的、
也没被登记。而项目页 `project_ui_tick` 每帧都轮询 `ui->aux`。
于是硬断线路径和退出路径上，页面还拿着一个指向已释放 session 的 aux 通道。
修法：两条路径都在 `ssh_disconnect` **之前**加 `if (g_pui) project_ui_close(g_pui);`
（顺带也让“Connection lost”横幅能露出来）。

### T4. `g_pui_touch_swallow` 命名不实 + 弹窗关闭漏设

该标志已不只服务项目页（AI 弹窗关闭也要用），改名 `g_touch_swallow`（5 处），
并在弹窗关闭分支补上置位——否则手指还按在屏幕上时，下一帧会被重新
命中测试到 ⚙ 徽标，在触控笔底下弹出设置页。

### T5. `ai_modal.c`：淡入途中关闭会先闪到全不透明

`ai_modal_close` 无条件把 `frame` 归零，而淡出曲线是
`256 - f*256/FADE_OUT_FRAMES`，**第一帧就是 256**。所以在 30 帧淡入
（首帧 eased 到 0）途中关闭，面板会先跳到完全不透明再开始变暗。

修法：新增 `out_from`，`close()` 在改相位**之前**记下当前 alpha，
淡出从该值插值下去。从 `OPEN` 关闭时 `out_from == 256`，原曲线不变。

**验证**：单行把 `out_from` 改回 `256` 复现旧行为，测试立刻报
`fade-out must start where fade-in left off: 46 -> 153`（46 就是淡入到第 5 帧的
实际不透明度，153 是闪到的全值）。

### T6. `ai_modal.c`：`visible` 兼作输入门闸 → 关闭后 0.2 s 键盘全死

`main.c` 把 `ai_modal_visible()` 同时用在两个**不同**的问题上：

- “面板还画着吗”（**布局**优先级：不许项目页盖上来）
- “键盘归谁”（**输入**路由）

对后者它是错的。`ai_modal_close()` 一被调用，语音状态立刻回 IDLE、
关闭动作已经执行完毕，但面板还要淡出 12 帧（≈0.2 s）。这 12 帧里
`ai_modal_visible()` 仍为真，于是**每一个按键、软键盘、全部触摸全被吞掉**——
用户关掉弹窗后立刻打字，头 0.2 s 的输入凭空消失。

新增 `ai_modal_captures_input()`（`FADE_IN` / `OPEN`，**不含** `FADE_OUT`），
`main.c` 的输入路由改用它，布局优先级继续用 `visible()`。
淡入仍然捕获输入——那是弹窗正在到来、用户正在读它被打开来看的答案。

### T7. `voice.c`：`VOICE_TYPING` 没有超时，半开连接转圈到永远

`TRANSCRIBING` 有 120 s 兜底（`VOICE_XFER_TIMEOUT_FRAMES`，`:706-708`），
`TYPING` 没有。它的循环在 `ssh_write` 返回 0（EAGAIN）时“下一帧重试同一字”，
**没有上限**；而 `main.c:2049-2050` 的通用卡顿检测器在 `voice_busy` 期间被
整个跳过，`voice_busy` 又**包含** `TYPING`。于是对端半开
（进程没了但没发 RST，或 TCP 窗口永久关死）时，转圈永不停，用户没有出路。

修法：新增**无进展**计数 `type_stall`（`enter_typing` 归零、每发出一字节归零、
仅在写入尝试返回 0 时自增）与 `VOICE_TYPING_STALL_FRAMES (5*60)`，
超时后 `enter_idle`。不能像 `TRANSCRIBING` 那样用整状态上限，因为一条长回复
合法地需要 `reply_len × type_delay` 帧；5 s 一个字节都没动，远超任何健康的
EAGAIN 停顿，而且放弃是无害的——转写本身已经成功，只是往 shell 的回放中止了。

### T8. `terminal.c`：SU / SD 的重复次数没有上限（ denial-of-service ）

`ESC[<n>S` / `ESC[<n>T`（SU/SD 整区上滚 / 下滚）原来是

```c
case 'S': for(int i=0;i<(p1?p1:1);i++) scroll_up_one(t); break;
case 'T': for(int i=0;i<(p1?p1:1);i++) scroll_down_one(t); break;
```

**T1 加的 `TERM_PARAM_MAX 9999` 只钳住了参数的「值」，没钳住「工作量」**：
每一次迭代都是一次 `(bot-top) × cols × sizeof(term_cell_t)` 的 memmove。
66×40 双屏网格下是 `39 × 66 × 12 = 30,888` 字节/次，× 9999 ≈ **309 MB**，
全部塞进**一帧**——3DS 是 268 MHz 的 ARM11，这是几十秒的界面冻结。
触发成本极低：`printf '\e[9999S'`。

其余重复类操作都已经有界，逐个核过：`X` 由 `x < cols` 限住；`P`/`@` 的
`end` / `mv` 在 n 很大时为负从而跳过 memmove（且语义正确：删/插到行尾）；
`L`/`M` 已由 T1 补了 `n > bot-cur_y` 的钳位；六个光标移动各有单侧/双侧钳位。
**`S` / `T` 是全项目仅剩的两处无界重复循环。**

修法：把次数钳到**区域高度**（xterm 的做法）——滚动超过区域高度与滚动
「正好一个区域高度」完全等价（内容早已全部滚出），于是工作量上限就是一个区域。

**验证**：这里有个坑值得记一笔——**光断言结果抓不到这个 bug**。滚 9999 次和
滚 4 次的最终画面完全相同（都清空了），所以「两种写法结果一致」的断言
在修复前后都是绿的。真正的性质是「工作量」。`scroll_up_one` 在 `top == 0`
时每次迭代会往 scrollback 环里推一行，于是**环的 `sb_size` 就是工作量的
确定性计数**：区域高度 4，钳位后应恰好推 4 行；未钳位会推 9999 行并把环
撑满 `TERM_SCROLLBACK`。用这个断言（而不是计时，计时会 flaky）后，
把钳位临时去掉，测试立刻报
`FAIL: a huge SU must do exactly one region's worth of work`。

### T9. `config.c`：字段按字节截断会把 CJK 字**劈成两半**

所有项目字段的上限都是**字节数**（`DSSH_PROJECT_PATH_MAX 128` 等），而一个
中日韩字要 3 个字节——所以按字节切大约**三次里有两次切在字中间**。被劈开的
是**非法 UTF-8**，它会一路写进 `settings.ini`，再被拼进 `cd <path>` 送进
shell：这不是"显示难看"，是一条**坏掉的 cd**。

`field_escape()`（写）、`next_field()`（读）、`copy_clamped()`（通用拷贝）
三处都是逐字节收尾。修法：新增 `utf8_fit()`，把截断长度回退到**最近的
码点边界**（从末尾倒着跨过续字节找到前导字节，整个序列放得下才保留；
放不下就丢掉那个半截字）。三处漏斗全部接上。

**定位过程值得记一笔**：第一版测试直接挂了，但我没有马上去改 `config.c`——
先写了个探针分两种情况跑：

| | 输入 | 修复前 | 修复后 |
|---|---|---|---|
| A | 126 字节（42 个汉字，**正好放得下**） | 原样往返，合法 | 原样往返，合法（无回归） |
| B | 127 字节（42 字 + 1 个悬空 `e4`） | 原样透传，`valid=0` | **126 字节，`valid=1`** |

结论是：**劈开动作发生在上游**（把字符串塞进结构体时那次 `snprintf`），
`config.c` 只是忠实透传。所以我没去改"错的那层"，而是让**写入文件的最后一关**
不再产出非法序列——这样无论上游给什么，`settings.ini` 里都不会有半截字。

### T10. `voice.c`：AI 问答缓冲区同样按字节截断，而且后果更远

T9 修完之后回头核「还有哪些**字节上限**会切 UTF-8」——`voice.c` 的
`ai_question`（`AI_Q_MAX 512`）与 `ai_answer`（`AI_A_MAX 4096`）是同一类，
而中文语音问答**必然**是中文。

`json_extract_string()` 是逐字节填的（`if (o < out_cap - 1) out[o++] = c;`），
`\uXXXX` 解出来的多字节序列也是按字节 emit，所以切在字中间大约三次两次。

**这里比 T9 更严重**：`ai_answer` 并不止显示在弹窗里——它会被
`build_history_json()` 折进**下一轮发给服务器的 history JSON**。JSON 字符串里
携带非法 UTF-8 会让整个请求被服务器拒绝，也就是**这一轮答完，下一轮直接问不了**。

修法与 T9 同：`voice_utf8_fit()` 在收尾处回退到码点边界，接在
`json_extract_string()` 与那段诊断 dump 上。

**验证说明（诚实交代）**：`voice.c` 依赖 3DS 的 mic/ndsp，**上不了宿主机**，
所以这条**没有集成测试**，只有编译通过 + 算法单独验证。算法我抄出来单跑过：
纯 CJK 0..60 全切点、ASCII+CJK 混合、全是续字节的退化输入（→0）、4 字节 emoji
（完整保留 / 切在 2、3 字节→0）全部落在边界上。

### T11. `project_ui.c`：同一类切字，而且在**卡片名**上最容易撞见

T9 / T10 收的是 `config.c` 与 `voice.c`。把同一把尺子量到 UI 层，
`project_ui.c` 有三个按字节收口的漏斗：

| 漏斗 | 上限 | 会被切的东西 |
|---|---|---|
| `copy_str()` | `PUI_PATH_MAX 160` → `DSSH_PROJECT_PATH_MAX 128` | `pwd` 探测回来的目录 |
| `path_basename()` | `DSSH_PROJECT_NAME_MAX 24` | 未命名卡片的**卡片名** |
| `append_bytes()` | 当前字段的 `field_cap()` | 软键盘输入的最后一个字 |

其中**卡片名只有 24 字节 = 8 个汉字**：一个 9 字的中文目录名（很常见）必然
被切，切完是 7 个完整字 + 2 个孤立续字节，渲染成一串 U+FFFD，并且**原样写进
`settings.ini`**。目录名/路径还会被当作 `cd` 目标发到 shell。

修法与 T9 / T10 同：模块内 `utf8_fit()`（**向后扫**，因为向前走的 `u8_next()`
遇到截断的 4 字节引导字节会读到上限外 3 个字节去），挂在上表三处。

**验证（有真测试，不像 T10）**：`project_ui.c` 不上 citro2d，可以上宿主机。
`tools/test_project_ui.c` 新增两条用例，用 `hstub_pwd` 灌一个 183 字节的
`/a/` + 60 个汉字的目录（3 字节前缀是关键——它让 128 字节上限**落在字中间**
而不是边界上）：

* `t_cjk_path_cap_does_not_split` — 断言落库路径是合法 UTF-8、长度 126（不是
  127）、且是原目录的前缀；
* `t_cjk_basename_does_not_split` — 断言卡片名是 7 个整字 21 字节。

反证：把三处 `utf8_fit` 调用撤掉，这 **4 条断言全红**；恢复后全绿。

### T12. `main.c`：设置保存的「失败退避」从来没生效，而项目页那条路径根本不看返回值

顺手核「两条保存路径语义不一致」时挖出来的，比原先记的那条更实在。两个问题：

**① 退避计时器每帧归零。** `settings_save_cooldown` 声明在 `main.c:1557`，
和 `stall_alert` / `ssh_dead` / `dual_term` 一起排在主循环体里 —— 那些是**每帧**
变量，它也是。于是 `:1822` 设的 `= 60` 在下一次循环开头就被重新初始化成 0，
`:1825` 的递减和 `:1828` 的清零全是死代码。结果：SD 卡写失败时会**每帧重试一次**
（≈60 次/秒），而 `:1805-1806` 的注释明说这个 cooldown 就是为了
「avoid per-frame spam if the card is busy」。

修法：改成 `static`。并让「设置页当前没待写」那条分支**递减**而不是**清零**，
否则项目页刚设的 cooldown 会被它一帧抹掉。

**② 项目页保存失败也照样清 `dirty`。** `:1719` 是
`settings_save(...); project_ui_clear_dirty(...);`，**不看返回值**。而
`settings_save()`（`config.c:531`）在 `fopen` 失败**或 `fclose` 失败**时返回 -1 ——
后者正是「卡写满了 / 卡被拔了」暴露的时机（刷盘在 fclose）。于是卡片编辑
**报告成已保存，实际没落盘**，而同一份文件里 `:1819` 那条路径是老老实实判了
返回值的。

修法：只在 `== 0` 时清 `dirty`，失败则设上 cooldown，等一秒重试。

**验证说明（诚实交代）**：`main.c` 依赖整套 3DS 运行时，**上不了宿主机**，这条
没有自动化测试。验证手段是：① 编译干净；② `settings_save` 的返回值语义逐行读过
（`config.c:531/534/576-578`，`fopen` 与 `fclose` 两处都返回 -1，成功返回 0）；
③ 「普通自动变量在循环体里每帧重新初始化」是 C 的基本语义，可确定。
**残留缺口**：页面关掉后 `dirty` 还留着，此时不再重试 —— 若卡在整个会话期间
一直写不进去，编辑仍会丢。要补的话得把重试挪到 `if (pui_up)` 之外，属于更大改动，
没擅自动。

### T13. `softkb.c`：设置项的多语言孪生数组比正主窄一格 → 越界读

设置项行里，正主是 `opts[SOFTKB_OPTS_MAX]`（`SOFTKB_OPTS_MAX` = 7），
五个语言的孪生数组却**写死 `[6]`**：

```c
const char *opts[SOFTKB_OPTS_MAX];              /* 7 */
const char *opts_en[6], *opts_ja[6], ... ;      /* 6  ← 窄一格 */
```

`set_lbl_arr5()`（`:1415`）用**同一个 i** 去索引正主和五个孪生，守卫是
`i > 6` —— **允许 6**。而吉祥物行 `nopts = 7`（关 / 屑屑 / 坤坤 / 菌菌 / 大眼 /
牛来 / 刀盾狗），于是英文下第 7 项读的是 `opts_en[6]`，**越界一个指针**，
正好落进下一个成员 `opts_ja[0]`。

**成因很清楚**：`source/softkb.c:1385` 的注释自己写着
「seven when 刀盾狗 pushed the mascot row to seven choices」——当初加第七个吉祥物
时把**取值上限**放宽到了 7，**孪生数组没跟着加宽**。

**这不是"潜在"问题，现在就在显示错字。** 按 `set_lbl_list()` 的回落顺序
`{EN, JA, KO, DE, FR, ZH}`（`:1356`）+ 结构体成员相邻关系，逐语言推出来的实际
显示（吉祥物行只初始化了 `.opts_en={"Off"}` / `.opts_de={"Aus"}` / `.opts_fr={"Off"}`）：

| 界面语言 | 越界读到 | 第 7 项（刀盾狗）实际显示 |
|---|---|---|
| 中文 | 不越界 | 刀盾狗 ✅ |
| 英文 | `opts_en[6]`→`opts_ja[0]`=NULL → `opts_ja[6]`→`opts_ko[0]`=NULL → `opts_ko[6]`→`opts_de[0]` | **Aus**（德语「关」）|
| 日文 | 同上路径 | **Aus** |
| 韩文 | `opts_ko[6]`→`opts_de[0]` | **Aus** |
| 德文 | `opts_de[6]`→`opts_fr[0]` | **Off** |
| 法文 | `opts_fr[6]`→`opt_desc_en[0]`=NULL → 回落到 KO | **Aus** |

修完之后（孪生数组加宽到 7，第 7 格为 NULL）回落链走到 ZH，五种语言都正确显示

（这一条最初被我误判为「越界读到 NULL，结果碰巧正确」，是 worker 给出具体落点后

修法：十个孪生数组统一改用 `SOFTKB_OPTS_MAX`（不再写字面量），并加两条
`_Static_assert` 把「孪生必须与正主同宽」钉成编译期约束。

**验证**：改回 `[6]` 后构建**直接失败**——

同一行结构里的相邻成员，运行期不会崩、也不会有人注意到。

### T14. `theme_ini.c`：`bad_key` 仍是字节截断，且「256 行」被误报成截断

这是「字节上限切 UTF-8」这一类**最后一处没收口**的地方（`config.c` / `voice.c` /
`project_ui.c` 都已在 T9–T11 修掉）。`note_invalid()` 把键名
`snprintf` 进 `bad_key[16]`，一个 6 汉字 + 1 字母的键（16 字节）就会被切在字中间，
而 `bad_key` 是要**显示在设置卡和启动横幅上的**。

同轮还发现一处逻辑错误：

```c
if (lineno == THEME_MAX_LINES && !feof(fp))   /* 判定"文件被截断" */
```

`feof()` 在这里**还没置位** —— 一个正好 256 行、末行以换行结尾的文件，读完第 256 行时
从未碰过 EOF，`feof()` 仍是 0。结果每个正好 256 行的文件都被报成「已截断」。

**验证**：`make test-theme-ini` 加两条用例（长 CJK 键名截断边界 / 正好 256 行不算截断）。
**反证**：把这两处修复撤掉 → 3 条断言失败（含 "got 15 bytes" 与 "invalid=1"）；恢复 → 全过。

### T15. `softkb.c`：`utf8_disp_cols()` 会读过头（潜在越界读）

```c
if (b >= 0xF0)      { cp = 0x10000; s += 4; }
else if (b >= 0xE0) { cp = ...;     s += 3; }
```

步长**只由首字节决定**，不校验续字节、也不看终止符。串尾只要有个截断序列
（任何上游字节上限都会造出这种串），`s += 3` 就直接跳过 NUL 继续读。
同文件的 `renderer.c:368 utf8_next()` 是有这个保护的，这里漏了。

**当前不可达**（已确认）：它消费的四个串都是字面量；T14 造出的非法 UTF-8 走的是
`renderer_draw_text_px_z` → `utf8_next()`（有 NUL 保护），不经过这里。
但 `settings_opt_rect` 那套右对齐数学迟早会接到动态串，所以顺手修了：
校验续字节，缺了就退化成 1 字节步长，对合法 UTF-8 结果完全一致。

### T17. `utf8_fit()` 四份副本收口成一个共享 `static inline`

T9 / T10 / T11 / T14 各修一处「字节上限切 UTF-8」，于是同一个 20 行函数在
`config.c`、`voice.c`、`project_ui.c`、`theme_ini.c` 里各长了一份。**四份副本就是

**四份副本的等价性是逐字节比对确认过的**，不是想当然：

| 模块 | 差异 |
|---|---|

**验证**：3DS 编译无新增 warning（唯一的 `-Wformat-truncation` 是记录过的既有项）；
14/14 宿主机测试通过。四份里**三份有回归测试兜着** —— `test-config-projects` 覆盖

### T18. `ime_init()` 只信文件头，不信文件长度

词典是 `romfs:/pinyin_dict.bin`（烘进 CIA，用户改不了），不是攻击面，
但**包损坏 / 写入中断**会造出一个截断的词典。而 `ime_init()` 的校验只有
magic `"PYIN"` + version 1 —— **截断的词典开头也是这两个**，照样通过。
之后 `entries[]` 和两个 pool 的指针全部按头文件里的偏移直接发下去，
第一次按键就 OOB 读。

`main.c:1472-1473` 明确写了「失败即降级为 passthrough，不致命」——
**正因为如此，这里必须拒**：接受一个坏词典，是把「没有输入法」变成「一按就崩」。

两处改动：

1. **`malloc(sz)` → `malloc(sz + 1)`，并 `blob[sz] = 0`。**
   pool 里是 NUL 分隔的串；最后一个串一直延伸到文件末尾时，**文件里没有终止符**。
   补的这一字节让 `strcmp`/`strncmp` 停在那里，而不是走进堆里。
2. **加边界校验**：`n_entries`、`pinyin_pool_off/len`、`word_pool_off/len`
   五个字段逐个对 `blob_size` 求交，任一越界就 `free` + 返回 NULL。

**测试**：`test_ime.sh` 原来只把真实词典喂进去，没有任何 fixture（这也是它
一直没发现这个问题原因）。补了 7 个用例：在 `build/` 里手搓一个合法的
2 条词典（ni→你 / wo→我），然后

- 5 个**必须被拒**：截断的 entry 表、`n_entries = 0xFFFFFFFF`、
  `pinyin_pool_off` 越过 EOF、`pinyin_pool_len` 越过 EOF、`word_pool_len` 越过 EOF；
- 2 个**必须被收**（防止边界校验矫枉过正）：原样合法词典、以及
  **末尾串不带 NUL、正好顶到文件末尾**的词典（第 1 处改动的正面用例）。

同时给 `test_ime.sh` 加了 `-fsanitize=address,undefined`（带探测降级，
和 `test_terminal.sh` 一个写法）—— 没有 ASan，这 7 个用例在 `-O2` 下会
**全部通过**，因为越界读在裸 `-O2` 里是静默的。

**反向验证**（撤掉改动看测试红不红）：

| 版本 | 结果 |
|---|---|
| 去掉边界校验 | **5 failures** —— 五个坏词典全部被接受 |
| 去掉补零字节 | ASan `heap-buffer-overflow`，exit 134 |
| 完整版 | 全绿，13 MB 真实词典在 ASan 下照常加载 |

布局用 `_Static_assert(sizeof(hdr)==28 / sizeof(ent)==12)` 钉住，
词典格式变了会编译失败而不是静静地编码出错。

### T19. `g_win_just_created` 是个会活过窗口的陈旧下标

X+Y+▲ 建窗口时置位（`main.c:674`），主循环在 `:1776` 用它把项目卡片页
抬起来。清零只有两处：`:1781`（抬成功后）、`:726`（`win_prune()`，整个会话没了）。

**漏的是第三种：窗口自己没了。** `win_pump` 里 channel 打开失败会走
`win_close()`（`:771`），而 `win_close()` 不清这个标志。

触发路径比较窄但要凑齐不难：AI 回答面板关闭后有 **12 帧淡出**，
期间 `modal_open` 仍为 1 而 `modal_capture` 已经是 0（`main.c:1630-1637`
把这两个谓词分开了）。和弦要求 `!modal_capture`，所以**淡出期间能建窗口**，
但 `:1776` 的抬起要求 `!modal_open`，于是被挡住。这 12 帧足够
`ssh_open_shell` 失败并 `win_close()` 掉那个槽位 —— 淡出一结束，
卡片页就为一个**已经不存在的窗口**弹出来，用户选卡后命令停进
`g_pending_cmd`，静默失效。

修法是在 `win_close()` 里补一句 `if (g_win_just_created == slot) g_win_just_created = -1;`。
这是**根因修法**（标志不再指向已退役的窗口），和 `win_prune()` 已有的先例一致，
而不是在抬起处再加一道判断去打补丁。

**验证**：这条是 3DS 上才跑得到的时序，宿主机测不了，靠读代码确认——
`win_close()` 的三条调用路径（`win_close_focused`、打开失败、shell 退出）
语义上都是「这个窗口要没了」，标志都不该再指向它。

## 十、第十五轮（T20 / T21）

### T20. `json_find_string_field()` 把不是 C 串的缓冲区当 C 串搜（P0，内存越界）

语音/AI 的回复落在 `v->reply_buf[8192]` 里，`ssh_aux_read()` 只推进 `reply_len`，
**从不写终止符**。而解析回复的 `json_find_string_field()` 用 `strstr(p, needle)`
找 `"question"` / `"answer"` —— `strstr` 是靠找 NUL 停下来的，于是：

- 回复**正好填满 8192 字节**时，整个缓冲区里一个 NUL 都没有，
  `strstr` 会扫过数组末尾，继续读 struct 后面的堆内容，直到撞见某个 0 字节；
- 回复没填满时也要看运气 —— 缓冲区是 `calloc` 出来的，上一次更长的回复留下的
  旧字节会充当"意外的终止符"，所以这个 bug 平时不发作。

这是本轮唯一一条**真正的内存越界**。触发条件是"AI 回答长到刚好填满 8 KB"，
不算罕见。

**修法**：写了个有界查找 `find_needle(hay, end, needle, nlen)`，
只在 `[hay, end)` 内匹配，取代 `strstr`。

**把它从 voice.c 里搬出来了。** voice.c 依赖 mic/ndsp，上不了宿主机，
这条修复就会永远没有测试兜着。而 `json_find_string_field` 是整条语音管线里
**唯一一段纯字节处理、没有任何 3DS 依赖**的代码，于是独立成
`source/json_find.c` + `.h`（沿用项目"逻辑尽量留在不依赖 citro2d 的 TU 里"的既有约定），
并配了 `tools/test_json_find.c` / `make test-json-find`（带 ASan）。

**测试 8 个用例**，其中三个是内存安全专项：
填满且无 NUL 的缓冲区、`body_len` 之后的陈旧字节不可见、needle 放不下就不该匹配。
其余覆盖正常解析、空白容错、`\n` / `\u4e2d` 转义、值里出现同名的诱饵 key、
以及 `out_cap` 截断时不能把汉字劈成两半（`utf8_fit` 那条路径）。

**反向验证**（撤掉修复换成 `strstr`）：ASan `heap-buffer-overflow`，exit 134。

### T22. 吉祥物的 ALERT 被打断后就再也回不来了

`mascot_set_recording(m, 0)` / `mascot_set_thinking(m, 0)` 都是直接
`enter_walk(m)` 收尾，而 `enter_walk()` 不看 `prev_state`。
只有 `mascot_set_reconnecting()` 手写了「如果之前是 ALERT 就恢复 ALERT」。

要命的是 main.c 那边是**边沿驱动**的：

```c
int want_alert = ssh_dead || interactive_stall;
if (want_alert != stall_alert) {          /* main.c:2093 */
    stall_alert = want_alert;
    mascot_set_alert(mc, stall_alert);
}
```

于是完整链路是：

1. 卡住 → `want_alert=1` → `mascot_set_alert(mc,1)` → `state = ALERT`，
   边沿已经用掉了（`stall_alert` 变 1）；
2. 用户按住 R 说话 → `mascot_set_recording(mc,1)` → `enter_record()` →
   `prev_state = ALERT`，`state = RECORD`；
3. 松手 → `mascot_set_recording(mc,0)` → `enter_walk()` → `state = WALK`；
4. 卡住仍在，`want_alert` 还是 1，但 `stall_alert` 已经是 1 ——
   **边沿不会再触发**，红叉就这么没了，而且等卡住解除时
   `mascot_set_alert(mc,0)` 发现 state 不是 ALERT，啥也不做。

转写态（THINK）同理。所以**在连接卡住时说一句话，红叉就永久消失**。

**修法不是给 `enter_walk` 加判断，而是把「退出临时态」收敛成一个函数**，
并且**用一个独立的 `alert_pending` 标志，不用 `prev_state`**：

```c
static void leave_temp_state(mascot_t *m) {
    if (m->alert_pending) { m->state = STATE_ALERT; m->alert_phase = 0; }
    else                  { enter_walk(m); }
}
```

**为什么不用 `prev_state`**：它是所有临时态共用的**一个**槽位。
`enter_type()` 在 RECORD 期间也会写它（`enter_type` 的早退清单里没有 RECORD），
一嵌套就把 ALERT 覆盖掉了。用 `alert_pending` 从根上绕开这个共享槽位。

三个出口（RECORD / THINK / LOOKUP）现在都走同一个函数 —— 这正是
「同一份状态有多处推导，其中一处漏了」那一类，收敛成单点才是根治。

### T23. `tcp_connect()` 把 DNS 返回的长度直接当 `memcpy` 长度

```c
memcpy(&addr.sin_addr, he->h_addr_list[0], (size_t)he->h_length);
```

目标 `addr.sin_addr` 是 **4 字节**，`he->h_length` 是解析器说的一个地址有多长。
`gethostbyname()` 按规范只回 AF_INET / 4，所以今天不会出事 ——
但这是个**未经校验的、来自外部的长度被当成拷贝长度**，后面跟着 8 字节
`sin_zero` 填充，真越界也就是溢出到栈上。顺手补了校验：

```c
if (he->h_addrtype != AF_INET || he->h_length != 4 ||
    !he->h_addr_list || !he->h_addr_list[0]) { ... }
```

放在 `socket()` 之前，这样失败时没有东西要回滚。

**验证**：不是可达缺陷，是纵深防御。改动不改变任何规范内的行为。

### T24. `ssh_write_slot()` 的循环没有"无进展"出口

```c
while (sent < len) {
    ssize_t n = libssh2_channel_write(ch, buf + sent, (size_t)(len - sent));
    if (n == LIBSSH2_ERROR_EAGAIN) break;
    ...
    sent += (int)n;
}
```

`n == 0` 时 `sent` 不前进，循环**永不退出**。这不是 libssh2 对 `len > 0`
承诺过的返回值，所以是防御性的 —— 但这个循环跑在**主循环的一帧之内**，
卡住的代价是整台机器冻住，而同文件里 `voice.c` 的 `flush_typing()`
自己就带了 `guard++ < 200`，说明作者知道这类循环要防。
补 `if (n == 0) break;`，语义等同 EAGAIN：报告已发出的字节，下帧再试。

### T25. `audio.c` 头部注释描述的是「5 个物种 + 分块布局」，代码是「6 个物种 + 交错布局」

文件头写的是：

```
 *   [1 .. 5]          FUNC  one per species
 *   [6 .. 10]         MOD   one per species
```

而 `mascot.h:54-60` 现在是 **6** 个物种
（`MASCOT_CRAB=0 … MASCOT_DOG`，然后是 `MASCOT_SPECIES_COUNT`），
`N_TOTAL = 1 + 2 * MASCOT_SPECIES_COUNT = 13`，代码里两处写的是
**交错**布局 `1 + 2*s` / `2 + 2*s`（不是分块的 `1+s` / `6+s`）。

也就是说这份注释讲了两件错事：**物种数量错**，而且**布局形状也错**。
同一段里「All 11 buffers … 10 baked slots … 5339..12288 samples … ~150 KB」
也全过期了（今天是 13 个 buffer、12 个 baked slot）。

**为什么这类漂移值得修**：`audio_play_key()` 的两处 `1 + (int)species * 2`
是**全项目唯一写死这个布局的地方**。谁加第 7 个宠物时，会先读这段注释，
然后照着「[1..6] FUNC / [7..12] MOD」去改 —— 于是 FUNC 和 MOD 会互相错位一整格，
而且听起来不会报错，只是每个宠物的叫声都串到隔壁。

**修法是让布局只在一个地方存在**：

```c
#define FUNC_SLOT(s) (1 + 2 * (int)(s))
#define MOD_SLOT(s)  (2 + 2 * (int)(s))
```

`audio_play_key()` 的 `switch` 两臂改成用这两个宏；注释改成引用宏而不是
复述数字，并且**刻意不写任何绝对数字**（"1 个 CHAR + 每个物种 2 个槽"，
剩下的交给 `MASCOT_SPECIES_COUNT` 和 `key_sound_*.h`）—— 因为绝对数字
正是这次过期的东西。

**顺带确认没有越界**：`audio_play_key()` 开头有
`if ((int)species < 0 || (int)species >= MASCOT_SPECIES_COUNT) species = MASCOT_CRAB;`
（:261-262），后面还有 `if (idx < 0 || idx >= N_TOTAL || !samples[idx].buf) return;`
（:287）。所以这一处**只有注释是错的，代码是对的** —— 但正因为代码没错、
注释错了，它才最危险：读注释的人不会去怀疑代码。

**验证**：`make` 重编译 `audio.c` 无新警告（只剩 `main.c:933` 那条既有的
`snprintf` `-Wformat-truncation`）；15 个 `make test-*` 全绿（本轮改动不
触及任何被测 TU，跑全套是回归保险）；`make cia` 产出 **14,717,888 B**，
与既有基线一致。

## 第十三节：settings.ini 的行缓冲与项目路径上限（T26 / T27）

前十二节扫的是逻辑缺陷，这一节扫的是「**上限值被钳制之后，那个数字又变成了
别人的长度**」——本项目里已经出现过一次（`audio.c` 的 N_TOTAL），这里又出现两次。

### T26. `settings_load()` 的行缓冲比最坏行长**短 70 字节**，而失败是静默的

`config.c:443`（改动前）：

```c
    /* A 9-field project row with every field at its cap is ~550 bytes
     * before escaping, so the old 512-byte line buffer would have
     * silently split the longest rows in half. */
    char line[1024];
```

这段注释记录了上一次修这个坑：有人发现 512 不够，提到 1024。**但他漏了转义。**
`field_escape()` 会把每个 `\` 和 `|` 写成两个字节，所以写出去的行最长是
字段上限之和的**两倍**：

| 项 | 字节 |
|---|---|
| `project_15 = ` | 13 |
| 6 个字段转义后（`2 x` 各上限） | 1040 |
| `raw` + `uses`(%d) + `last_used`(%ld) | 32 |
| 8 个 `\|` 分隔 + 换行 | 9 |
| **最坏合计** | **1093** |

而 `fgets(line, 1024, fp)` 最多读 **1023** 字节 —— **短 70**。

**失败方式才是重点**：溢出的行被切成两段。第一段带 `=`，被解析成一条
字段被砍断的畸形行；第二段**没有 `=`**，于是 `if (!eq) continue;` 直接跳过。
结果是**卡片静默损坏**——路径被截、命令被截——而且下次保存会把这个畸形值
原样写回去。没有报错，没有任何信号。

**修法：让缓冲从上限推导，而不是再猜一个数**：

```c
#define PROJECT_ROW_MAX                                                     \
    (2 * ((size_t)DSSH_PROJECT_NAME_MAX + DSSH_PROJECT_PATH_MAX +           \
          DSSH_PROJECT_TOOL_MAX + DSSH_PROJECT_ARGS_MAX +                   \
          DSSH_PROJECT_CMD_MAX + DSSH_PROJECT_NOTE_MAX) + 160)
    char line[PROJECT_ROW_MAX];
```

**今天这笔账是不容易被触发的**（要凑够约 450 个反斜杠/竖杠才溢出 1023），
但它是**潜伏**的：任何人上调一个字段上限就会立刻变成活跃缺陷 —— 而我在
修 T27 时正要上调 `DSSH_PROJECT_PATH_MAX`。所以顺序是先修 T26 再修 T27。

### T27. `pwd` 探测缓冲（160）比卡片存储字段（128）大 32 字节

`project_ui.c` 的 `PUI_PATH_MAX` 是 **160**，项目卡的
`DSSH_PROJECT_PATH_MAX` 是 **128**。而"使用当前目录"这条路径是
`copy_str(ui->draft.path, sizeof(ui->draft.path), c)` —— 从 160 直接拷进 128。

于是：**你站在一个长目录里，点"使用当前目录"，存下来的 `cd` 目标是你实际
所在目录的一个前缀**，而界面上什么都不会说。

更糟的是这件事**本来是有检测手段的**。`config.c:235` 的 `copy_clamped()`
注释写着：

> Returns the number of bytes copied (excluding the NUL) so callers can detect truncation.

而 `:415-420` 六个字段的调用点**一个都没有接这个返回值**：

```c
    copy_clamped(out->name, sizeof(out->name), name);
    copy_clamped(out->path, sizeof(out->path), path);
    ...
```

API 专门为检测截断留了出口，所有调用方都把它扔了。`project_ui.c` 里的
`copy_str()` 更直接，返回 `void`。

**修法**：

1. `DSSH_PROJECT_PATH_MAX` 128 → **160**，与 `PUI_PATH_MAX` 对齐；
2. 在 `project_ui.c` 加一条静态断言，把"探测缓冲不得大于存储字段"变成编译期约束：

```c
_Static_assert(DSSH_PROJECT_PATH_MAX >= PUI_PATH_MAX,
               "PUI_PATH_MAX must not exceed DSSH_PROJECT_PATH_MAX");
```

之所以必须加这条：上限改成 160 只解决了**今天**的对齐；下次有人把探测缓冲
调到 200、或者把字段缩回 128，截断会原样回来，而 `copy_clamped` 的返回值
至今没人接。**这条断言是目前唯一挡在它前面的东西。**

### 顺带：测试里硬编码的 126 立刻就过期了

`tools/test_project_ui.c` 原本断言 `strlen(...path) == 126`，注释写着
"draft.path holds 127 bytes"。上限一改 128→160，这条断言**当场失败** ——
和 `audio.c` 那次一模一样：绝对数字写在第二处，第一处改了它不会跟着改。
已改成从 `DSSH_PROJECT_PATH_MAX` 推导。

（附带发现：cap 改成 160 之后 `159 - 3 = 156`，正好被 3 整除，刀口落在
字形**边界上**而不是中间，这条用例不再触发回退逻辑。已在注释里写明，

**验证**：`make` 重编译无新警告（只剩 `main.c:933` 既有那条）；
`_Static_assert` 通过（说明 160 ≥ 160 成立）。

### T31. `to_ctrl()` 的返回值既当数据又当哨兵 —— Ctrl-Space 发不出 NUL

```c
static char to_ctrl(char c) {
    ...
    if (c == ' ' || c == '@') return 0x00;     /* Ctrl-Space = NUL */
    ...
    return 0;                                   /* "无映射" 也是 0 */
}
```

调用方：

```c
if (is_ctrl) {
    char x = to_ctrl(c);
    if (x == 0) return emit_byte(k, c);  /* 0 被当成"无映射" → 退回字面量 */
```

于是 Ctrl-Space / Ctrl-@ 发出的是空格和 `@`，**注释里写的 NUL 永远到不了**。

**但只修 to_ctrl 不够**：就算发出 `0x00`，消费方是

```c
send_to_ssh(ssh, g_focus, out, (int)strlen(out), mc);
```

`strlen` 遇到首字节 0 就是 0 —— 这个键会被**量成 0 字节**，照样发不出去。

所以完整修法是三处：
1. `to_ctrl()` 改返回 `int`，"无映射"用 **-1**；
2. 新增 `keyboard_out_len()` 暴露 `out_len`（`emit_*` 一直在维护它，
   只是没有公开访问器）；
3. main.c 改用 `keyboard_out_len()` 而不是 `strlen()`。

**验证**：test-keyboard 现在断言 `out[0] == 0x00 && out_len == 1`，
并特意注明了"这一字节的 strlen 是 0"。30 条断言全绿。

### T32. 项目页借用软键盘时，⚙ 徽章能把设置页在背后打开（按键劫持）

const char *name = p->name[0] ? p->name

**下屏早就有回退，而且带中英文**。空名称卡片既不空白，也不是不可点。我此前

renderer_draw_text_px_scaled(tx, y - 2,

同一个页面里三处取名逻辑，三种写法：

### 修法：收敛成单点 `card_display_name()`

```c
static const char *card_display_name(const project_ui_t *ui,
                                     const dssh_project_t *p,
                                     char *buf, size_t buf_sz) {
    if (p->name[0]) return p->name;
    if (p->path[0]) {
        path_basename(p->path, buf, buf_sz);
        if (buf[0]) return buf;
    }
    return ui->lang == L_ZH ? "(未命名)" : "(unnamed)";
}
```

顺带把回退链补成 `name → 路径末段 → 占位文案`。中间那级不是我拍脑袋加的：
`commit_draft()`（`:782-789`）在保存时就是先取目录末段、再退回 tool
或 `"card"`，所以显示成目录名，**卡片在保存前后读起来是一样的**。

## 第十七节：JSON **写**方向的对称补强（T35 / T35b）

### 抽取

T20 抽的是**读**（服务端 → 3DS）。这次补**写**（3DS → 服务端的 history JSON）。
新增 `source/json_build.{c,h}`（从 voice.c 搬出 `json_append_string` /
`build_history_json`）、`tools/test_json_build.{c,sh}`、`make test-json-build`（共 18 个）。

因为 `voice_t` 在 voice.c 外不透明，history 接口改成中性结构
`json_history_entry_t { const char *question, *answer; }`，并导出
`JSON_STRING_ESCAPE_MAX 6`（`\u00XX` 的宽度，`json_build.h:42`）。

### 缺陷 1（中）`voice_ai_close_keep()` 字节截断没过 `utf8_fit()`

`voice.c:529/532` 原本是纯 `snprintf` 拷进 `ai_hist_q/a[]` —— 纯字节截断。
而同模块注释 `voice.c:165-177` 白纸黑字写着这条规则（AI 缓冲区按字节、
CJK 一个字 3 字节，字节级截断三分之二劈在字形中间，剩下的非法 UTF-8 会
折进下一轮发给服务端的 JSON）。注释还说 "both call sites"，实际只有一处，已陈旧。

后果被服务端 `whisper_shim.py:477` 的 `.decode("utf-8", errors="replace")`
兜住（已核实），所以不是崩溃 —— 是**砍半的字形变 U+FFFD 喂进 DeepSeek 上下文**。

### 缺陷 2（真且可达）history 缓冲按"输入长度"而非"转义后长度"定值

`voice.c` 原注释：`History JSON max = 5 * (~5 KB Q+A overhead with escaping)
≈ 30 KB. Allocate generously: 4 + pcm_len + 64 KB`。那个 ≈30 KB 是**未转义**
尺寸（实测纯文本 5 轮 23071 字节），但控制字节转义后要 **6** 字节。
实测 `5 轮全 0x1f, cap=65536 → -1`，最坏需 **138221 字节**，超一倍。

**可达性我自己回代码核过**（这是它能不能算真缺陷的关键）：
`voice.c:390-393` 解析失败时把**服务端发来的原始 reply_buf** 倒进
`ai_answer`，再由 `close_keep` 拷进 `ai_hist_a[]`。所以服务端可控字节进得去；
下一轮溢出 → `enter_error("ai hist json")`，**整次 AI 提问在 3DS 上直接死**。

修：`JSON_HISTORY_CAP(n,q,a)`（`json_build.h:55-56`），`voice.c:299` 用它。

### 实测是好的（别只记缺陷）

- **没有缓冲区溢出**：四条边界分支（开引号 `p>=cap-1` / 转义 `p+el>=cap-1` /
  普通 `p>=cap-2` / 闭引号）严格度一致，都要求写完后 `p<=cap-2`。
- **U+2028/29 不转义是有意的**（消费方是 `json.loads` 不是浏览器 JS）。
- **截断不劈字形** —— 该函数是"全有或全无"，放不下就 -1 且 `*pos` 不动。

### T35b：测试里第二份常量副本 —— 承重，且**静默失效**

worker 第一版在 `test_json_build.c` 抄了第二份 `AI_Q_MAX 512 / AI_A_MAX 4096 /
AI_HISTORY_MAX 5` 和第二份尺寸公式。它不是普通重复，是**缺陷 2 回归测试的承重墙**：
常量一改，测试验的数字就和运行时 malloc 的大小脱钩，**而且照样全绿**。

收口：常量搬到 `source/voice.h:21-23`（该头文件只依赖 `<stdint.h>`，
宿主机测试可直接 include），公式收进 `json_build.h:55-56`。
反向验证：`AI_A_MAX` 改 8192 → 两边同步放大到 **261184**，测试仍全绿。

**这是"绝对值写在第二个地方"在本项目的第 4 次出现**（audio.c 的 N_TOTAL 散文、
`test_project_ui.c` 的 126、`config.c` 的 `line[1024]`、这次的 AI_*）。
**规则：测试里出现 "Mirror of ..." 字样的常量，一律视为待修。**

1. **aux channel 泄漏（真缺陷）**。`ssh_aux_close`（原 `:800-807`）在非阻塞态
   `channel_close` + `channel_free`，而同一个文件 `:745-747` 自己写明了规则：

   3DS 主循环单线程跑渲染，这就是整机卡死、只能硬重启。
   *修法*：`SSH_BLOCKING_IO_MAX_SPINS 30000`（每轮睡 1 ms ≈ 30 s），超限返回
   `-EIO` —— 与 `map_ts3ds_result`（`:62-70`）把非 AGAIN 一律压成 `-EIO` 的

### T43. 机器选择页没有滚动窗口 —— 8 台时后 3 行**根本不画**

**问题.** `machine_ui_draw_bot()` 从 `M_LIST_Y0 = 24` 按 `M_ROW_H = 40` 画**全部
n 行**，`h = M_ROW_H - 6`。下屏高 240，`DSSH_MACHINES_MAX = 8`：

| 行 | 条带 y 区间 | 结果 |
|---|---|---|
| 0–4 | 24–217 | 正常 |
| 5 | 224–257 | **起点正好压在 y=224 的底栏提示文字上**，且被 240 截断 |
| 6 / 7 | 264 / 304 | **完全在屏外** |

而 `machine_ui_tick()` 的 D-pad 是 `cursor = (cursor ± 1 + n) % n`，**能走到第 8 台**。
实测（8 台配置）：走到底后屏幕上**一个 accent 像素都没有**——高亮行不存在，
用户只能读上屏的「7 / 8」猜。对照 `project_ui.c:618-628` 的 `nav_clamp()`：
`list_first` + `CARD_VIS = 5` 的钳制 + `clampi(list_first, 0, n - CARD_VIS)`，
机器页**缺的正是这一层**（8 台比 5 张卡片还多，更该有）。

**修复.** 加 `M_H = 34` / `M_VIS = 5` / `M_FOOTER_Y = 224` 与 `first` 字段，
`mui_clamp()` 照 `nav_clamp()` 的形状写；`draw_bot()` 只画窗口内的 5 行。
顺带把行号改成 1-based（上屏写「3 / 8」，下屏原来从 0 编号，指向的不是同一台）。

**验证.** `tools/test_machine_ui.c` 新增 `t_eight_machines_scroll()`：逐 slot 断言
条带存在、**y=224..239 整条底栏带必须保持 `bottom_bg`**、7 次 DOWN 后第 8 台
在窗口内且高亮行确实有 accent 像素。反向对照：把 `M_VIS` 改回 8 → **20 条失败**
（含全部 16 条底栏带断言）。

### T46. 切机器不把该机设置推给活 UI —— 而且下一次改设置会**覆盖写回**

**问题.** `connect_and_open()` 载入新机器的 `settings.<N>.ini` 到
`g_loaded_settings` 就完事，**没有** `softkb_apply_settings()`。而 softkb
才是全应用读主题 / 语言 / 吉祥物 / 录音上限的地方（`main.c` 每帧从它同步
终端主题、键盘、录音器），`softkb_apply_settings()` 全项目只在启动时
（`main.c:1437`）被调用过一次。两个后果：

1. 切到机器 N 后，**机器 N 的主题 / 界面语言 / 吉祥物 / 录音上限不生效**，
   要等下次启动；
2. 更糟：设置页保存走的是「重载文件 → `softkb_export_settings(kb, &st)` 覆盖
   → 写回」，而 `kb` 里还是**机器 0 的值** → 在机器 N 上动任何一个设置项，
   都会把机器 0 的偏好**写进机器 N 的 settings.<N>.ini**。每机器一份设置文件
   的意义被抹掉。

**修复.** `connect_and_open()` 载入后补 `softkb_apply_settings(kb, &g_loaded_settings)`，
每帧的同步逻辑自然把主题 / 键盘 / 录音器带走。它同时清 `settings_dirty`，
在这里不可达（到达本函数必须机器页在场，而机器页整帧吃输入，设置页不可能
同时有未落盘的编辑）——注释里写明了这条推理。

**验证.** 本机**无法**用宿主机测试覆盖：`main.c` 不参与宿主机构建，
`softkb.c` 拉 citro2d 进不了宿主二进制。已做的：两处调用点成对写注释互相指认
（启动处指向 `connect_and_open()`，反之亦然），并用
`arm-none-eabi-objdump -dr build/main.o | grep -c "bl.*<softkb_apply_settings>"`
确认为 **2** 个调用点（改前是 1）。**待真机确认**：换机器后主题立刻变。

### T47. `config_save_selected()`：截断式写 + 8 KB 上限 + 吞掉空行

**问题.** 这个函数**每次连接都会跑**（启动、机器页确认、SELECT 重连），
而它重写的是**存着密码的** `config.ini`。三处：

1. `fopen(path, "w")` 直接截断再写，**没有临时文件**：写一半失败（卡满/被拔）
   就把凭据文件毁了；
2. `char in[8192]` 定长读入 → 超过 8191 字节的文件**尾部静默丢失**，重写后
   尾部那些机器**被删掉**。可达：每台 5 行、`macos_keychain_password_N` 最长
   256 字符 + 前缀 ≈ 284 B/行，8 台 × 5 行 ≈ 11.4 KB > 8192；
3. `strtok_r(in, "\n", ...)` 跳过空 token → **每次连接都把用户文件里的空行抹掉**，
   手写的分节全被压平。

**修复.** 动态缓冲整体读入（无上限）；逐行重建、**除那一行外逐字节原样复制**
（注释、空行、键序、CRLF 全保留）；`is_selected_machine_line()` 允许前导空白
并认 `\r`/`\n` 结尾，且不会把 `selected_machine_backup` 误当正主；文件里已经
是这台机器时**直接返回不写**（常见情形下彻底不碰凭据文件）；否则写 `path.tmp`
再 `rename()`；`rename()` 在不认它的 FAT 后端上会失败 → **回退到原来的就地重写**，
所以最坏情况等于旧行为，不引入回归。另加一个 `fopen(path, "a")` 的可写性探针，
保住 `config.h` 里「unwritable file is ignored」这条既有契约（否则
`rename()` 会绕过只读位——目录可写就够了）。

**验证.** `tools/test_config.c` 新增一组：注释/空行/缩进赋值/同名前缀键、
无末尾换行的追加、`chmod 0444` 双向（值相同 → 返回 0 且不写；值不同 → 返回 -1）、
以及一个 **>8 KB 的八机器夹具**（断言 8 台全在、最后一台的凭据也在）。
反向对照：把读入限回 8191 字节 → 「including the last machine's credentials」
失败（尾部被删，正是这条缺陷的形状）。

### T53. citro2d 做深度测试：双行布局在真机上整行不可见（只在设备上出现）

- **症状.** DARK 主题 + 8 台机器（5 个 `name_N`）跑一遍，下屏 **有名字的行全是
  空条**：选中行整条是 `key_accent` 填充、安静行整条是 `panel_bg` 填充，一个字都
  没有；**没名字的行（单行回退）显示正常**。
- **证据（设备侧读数）.** 对选中行条带做逐扫描线颜色统计：`ly=22..51` 每一条都
  是 `rgb(136,197,232)`、`nonmode=0`（244 个采样点里没有一个不是填充色）。修后
  同一条带：`ly=24..35` 与 `ly=41..48` 各有一段墨（`nonmode` 16..55），中间
  `ly=36..40`、`ly=49..51` 干净——正是两行。
- **根因.** `citro2d` **按 z 做深度测试**，z 低于已写入表面的图元**不是「被盖住」
  而是根本不画**。`source/machine_ui.c` 里双行文字写在 z 0.55 / 0.50，而行条带
  填充写在 0.60 —— 填充先把深度写近，文字就整条丢失。单行回退恰好是 0.70，所以
  只有它活下来。**这也解释了「为什么只有有名字的行坏」**：无名字走的是另一个
  分支、另一个 z。
- **宿主机为什么看不见.** `tools/stub/pui_host_stubs.c` 的 `renderer_draw_text_px_z()`
  当时写着 `(void)z;` —— 桩把 z 丢掉、按调用顺序合成。这正是这个页面能在宿主机上
  跑测试的原因，也正是它藏住这个缺陷的原因。**桩比真实现宽松，是一个测试能力
  缺口，不是一个小疏忽。**
- **修.** ① `machine_ui.c` 引入一组具名深度常量并重写全部 30 处 z 字面量，让顺序
  严格递增：`MZ_PAGE 0.10 < MZ_SURFACE 0.20 < MZ_EDGE 0.30 < MZ_GLYPH 0.40 <
  MZ_TEXT 0.50 < MZ_TEXT_HI 0.55`。用具名常量而不是字面量，理由和 `project_ui.c`
  一样：**一个只在相邻关系里有意义的数字，写成五处的 `0.55f` 是没法评审的**。
  ② 给桩加深度缓冲，按 GPU 的规则丢弃「z 更低」的写入。
- **桩的两个坑（都踩了）.** ① 「空」哨兵必须取**远平面**：citro2d 是 z 越大越前，
  初值写成 `1e9f` 等于「每个像素最近处已经有个东西」，于是第一次写入全部被丢弃、
  整屏读成空 → 一次 76/275 失败。改成 `-1e9f` 才对。② 桩的**测试模式必须存原色、
  不能合成**：`panel_bg` 这类深色只差 1 无所谓，但 0x55 透明度的分隔线会被合成成
  「既不是调色板常量、也不是设备真会产生的值」（设备在浮点里混合），断言就变成了
  对一个虚构值下判断 → 7/275 失败。现在只有预览模式（`hstub_paint_text`）合成。
- **反向对照（这一条才是重点）.** 把 `MZ_SURFACE` 从 0.20 改回 0.60（复现修前的
  顺序）→ `make test-machine-ui` **失败**，且失败在 `the name is drawn in the upper
  band` / `the address is drawn in the lower band` 这类断言上。**加深度缓冲之前，
  同一个补丁是全绿的**——这就是「宿主机现在能抓住这类缺陷」的证明。
- **验证.** 修前设备截图 `e2e_named_dark/settled.png`（同一份 fixture，
  `config.ini md5 = a253fed737be95b1029e2707a947a094`）与修后 `e2e_fix_named_dark/`

### T54. 模拟器截图是 Display P3，源码常量是 sRGB —— 比色前必须先转

- **症状（假警报）.** 修完之后，选中行条带的填充读数是 `rgb(136,197,232)`，而
  DARK 的 `key_accent` 是 `0x74c7ec = (116,199,236)`，相差 20 —— 读数工具报
  `?? rgb`，看起来像「选中行用了错的底色」。同时每个深色都恰好低 1：
  `bottom_bg` 源码 `(24,24,37)` 读出 `(24,24,36)`，`panel_bg` `(30,30,46)` 读出
  `(30,30,45)`，`ink_dark` `(17,17,27)` 读出 `(17,17,26)`。
- **排查过程（值得记住的两次否定）.** ① 先怀疑是全局变换，于是拿「源码已知的
  大面积纯色」反推：`ink_dark` 的最深像素是 `(17,17,26)`，与源码只差 1 —— 任何
  gamma 变换都会把 17 抬到 28 左右，所以**不是 gamma**。② 再拿 `key_accent` 的
  三个通道去拟合单个 gamma：R 需要 g≈0.80、G 需要 g≈1.04，**一个 gamma 拟合不了**，
  所以也不是 gamma。③ 于是按 sRGB→Display P3 的标准矩阵手算
  `(116,199,236)` → **(135.7, 197.0, 232.1)**，与读数 `(136,197,232)` 逐通道吻合；
  `bottom_bg` → **(24.0, 24.0, 36.0)**，也吻合。**结论：应用的颜色是准的，是截图的
  色彩空间不同。**
- **SOLAR 独立复核.** SOLAR 的 `key_accent` 是 `0x268bd2 = (38,139,210)`，设备读出
  `(70,137,204)` —— 按 sRGB 比是差 32 的大错，转 P3 后落在容差内并被正确判为
  `SELECTED`。**两个不同饱和度的颜色都只有转 P3 才吻合，这个解释站得住。**
- **修.** 读数工具加 `srgb_to_p3()`，所有「源码常量 vs 截图」的比较一律先转。
- **方法论结论（比这个 bug 本身重要）.** 直接拿源码常量跟截图比色，**深色只差 1
  （容差盖得住）、饱和色能差 20~32（容差盖不住）**——于是「底色不对」这类假警报
  **只会出现在饱和主题上**。单看 DARK 很容易得出「容差调大点就行」的错误结论。

### T55. 读数工具自己有四个错误（两个会产生假警报）

- **① 12 px 窗口判「几行字」→ 两行读成一行.** 窗口从条带**顶边**起算，而
  `dy=0..1` 是 1 px 描边：描边色离 `panel_bg` 很远，于是**安静行被读成
  `lines=1`（其实是边框）**；同时两行分别占 `dy≈4..15` 和 `19..28`、相距 15 px，
  12 px 的窗口从 `dy=8` 起会同时含两行，**两组被并成一条**。改成**按扫描线**判：
  逐条问「这条线上有没有墨」，再把相邻的并起来——一行字的物理高度就是它自己的
  高度，与另一行隔多远无关。
- **② 用固定容差判「是不是底色」→ 只找到 1 条条带.** DARK 的 `panel_bg(30,30,45)`
  与页面底色 `(24,24,36)` 只差 8，而 gap 行是 `(27,27,41)`、差 5。任何固定容差
  要么把 panel 条带误判成底色（容差 8 时 5 条条带只找到 1 条），要么把 gap 行误判
  成条带。改成比**相对距离**（离底色近还是离条带填充近），不需要容差。
- **③ `locate_top` 用「最长亮段」→ 命中 macOS 窗口标题栏.** 标题栏纯白、横贯
  整幅，`y0` 被读成 33（真实约 100），于是「标题带的墨色」采到标题栏、读出
  `rgb(255,255,255)`。**一个纯白读数在 DARK 主题里根本不该存在，正是它暴露了
  定位错了**——不是应用画错了。改成找「大片等于底屏底色的区域」，并加自检：
  顶屏比例与底屏比例差 0.04%（应当相等，都是模拟器的同一个缩放）。
- **④ 原点不可信 → 改成每行用「自己的顶边框」定位.** 实测 `locate_bottom` 给的
  `bt` 偏低约 4.4 逻辑 px（≈13 物理 px）：五条条带顶边框在
  `897/1016/1134/1252/1371`，相邻差 118.5 物理 px，而 `M_ROW_H=40`，于是真实比例
  `= 118.5/40 = 2.9625`、真实原点 `= 897 - 24*2.9625 ≈ 826`，不是 839。
  **比例对、原点偏**，所以行距量得准、绝对位置量不准。现在每行以**自己的顶边框**
  为原点量行内的一切（相对量），并把量到的行距 `[39.9, 40.3, 39.9, 39.9]` 打出来
  自检——**布局真的漂了它仍然会失败**，不会静默跟随。

## 第二十五节：补 `name_N` 文档时挖出的三件事（T56–T58）

起因是给 `sd_template/3ds/3dssh/config.ini.example` 补 `name_N` 的说明行。**文档句本身
就是断言**，所以每写一句都回代码核了一遍，结果三处与我的初稿不符。

### T56 单位漂移：上限是 31 **字节**，不是 31 个字符

初稿写「Names are capped at 31 characters」。`set_str_n()`（`config.c:65-68`）是
`snprintf(dst, n, "%s", src)`，`name` 字段宽 `DSSH_MACHINE_NAME_MAX`（`config.h:51`）= 32，
所以砍的是 **31 字节**。31 字节 = 31 个拉丁字母，但只有 10 个汉字。

### T57 同一个上限、两条路径语义不同（读文件这条路会存进非法 UTF-8）—— **已修**

**发现**（补 `name_N` 文档时核出来的）：

- **设备改名路径**：`draft_append()`（`machine_ui.c:259-268`）末尾 `buf[utf8_fit(buf, len)] = 0`
  —— 截断落在**码点边界**上，`utf8_fit.h` 是全局唯一那份回退。
- **读文件路径**：`set_str_n()` 的 `snprintf` **按字节**截断，不看边界。手写一个超长非 ASCII
  `name_N` 时，31 字节的切点落在某个 3 字节汉字的**第一个字节**上，于是
  `ssh_machine_t.name` 里存的是**非法 UTF-8**；绘制侧 `tf_text_clip()`（`text_fit.h:68`）
  走严格的 `utf8_next()`，把那个孤立首字节画成 **U+FFFD 替换字**——不崩、不空，但用户看到
  一个「�」。**同一份 `name` 字段，两条写入路径对同一个上限的语义不一致。**

**修法**（用户「继续」后动手）：`set_str_n()` 末尾补一行

```c
    dst[utf8_fit(dst, strlen(dst))] = 0;
```

这是**全程序最后一个没过 `utf8_fit` 的字节上限** —— `utf8_fit.h` 的注释本身就点着 config.c。
ASCII 完全不受影响（两个 ASCII 字节之间的切点本来就是码点边界，`utf8_fit()` 原样返回长度），
只有超长非 ASCII 值会移动，且最多移动 3 字节。

**宿主机证据**

- `tools/test_config.c` 把原先「钉住当前（错误）行为」的三条断言翻成正确期望：
  `strlen == utf8_fit(CJK, 31)`（= 30）、`[29]` 是延续字节、以及「这个名字以自己的长度为
  拟合长度 ⇒ 结束在码点边界 ⇒ 是合法 UTF-8」（用共享的 `utf8_fit` 当判据，不引入第二个解码器）。
  断言刻意**绑在共享规则上而不是绑在数字上**：把 `set_str_n` 退回裸 `snprintf`，这里就是
  31 对 30、必然失败。
- **反向对照**：删掉那一行重编 → 正好失败这 2 条（`2 of 210 config test(s) failed`），
  其余 208 条一动不动；还原后源码字节一致。config 套件 **192 → 210 条**，五套宿主机全绿。

**产物证据**（`utf8_fit` 是 `static inline`，没有可数的 `bl` 调用点，所以换判据）

- `build/config.o` 里 `utf8_fit` 的特征掩码 `and #192/#224/#240/#248`：**21 → 35**；
  并多出一个 `.text.set_str_n.part.0`（300 B）。A/B 反向对照：删掉那一行 → 掩码回到 21、
  该节消失。
- 顺带解释了一个反直觉现象：**elf 文件反而小了 2,040 B**（6,378,784 → 6,376,744）。
  但 `elf .text` 其实**大了 392 B** —— 函数变大到超过内联阈值后 GCC 改为外提一份共享副本，
  `config_load` 因此瘦了 344 B。**那 2 KB 差异不在代码里，是段对齐/偏移的抖动**，
  正好又一次印证「size 不能当改动进包判据」。

**设备侧证据**（Azahar；静态页面按 skill §4.5 不用电影；夹具 `build/.verify/fixture-overlong-20260920/`）

## 第二十六节：真机「启动卡住」四件事（T59–T62）

### 报告与症状

> 「安装这个 cia 到真机后，真机启动时卡住了，说明你没有做好升级策略吧，此前的
> config 和当前不一致了，需要处理」

「卡住」的字面含义故意留宽：可以是黑屏、可以是停在横幅后不动、也可以是停在
死掉的终端。我们**没有真机**，所以接下来这句话要先说清楚：

- 我们能复现的，是**同一个症状家族里两个机制**（T59、T60），它们都在设备侧
  留下了屏幕截图（见下表），用户报告的"卡住"很可能就是其中之一或两者相加。
- 模拟器**没有重现**的是这两个机制在真机上的**额外放大**：SD 卡时序、`sdmc:`
  挂载延迟、`socInit` 在 NWM 未连接时的行为等。换句话说，模拟器复现的是
  **「同代码、同内存、同逻辑」下的等价现象**，不是真机本身。

### T59. `machine_count == 0` 是一条**静默死路**（P0，已修）

**症状**：把 `config.ini` 拿走（或文件不可读、或 `sdmc:` 整张 SD 没挂上、或
目录不存在、或权限不允许），开机后——

```
DSSH  ● pinyin IME (on-screen 拼/EN)  ● voice (hold R to record)
START+L 双屏一体终端 ...  Circle Pad 滚动
loading pinyin dictionary...
dictionary loaded.
[光标]
```

—— **没 picker、没报错、没提示**。机器选择页在 `machine_count > 1` 才开，
所以 0 台既不打 picker；`connect_and_open(0, ...)` 里 `idx >= g_cfg.machine_count`
直接 `return` 不动 `*pssh`，等于什么都没发生。

**根因（两层）**：

1. `config_load()` 打开失败时 `return 0`，**跳过**末尾 `machine_count` 计算，
   所以 missing file → `machine_count = 0`。这是 **§1 当时判定的"对"**——
   当时的语义是「占位 `your-server.example.com` 不算配置好的机器，所以
   missing file 不该假装有一台」。
2. 但 **没人写下游**。`connect_and_open(0, ...)` 在 `idx >= machine_count`
   时**一言不发**地 return，调用方看着像是 idle_loop 起得特别安静。

**修法（main.c）**：

- `config_load()` 的返回值改成 `int config_found` 被 main() 记下。
- 在决定走 picker 还是走 `connect_and_open` 之前，先判 `machine_count == 0`：
  区分两种写法（文件读了但没 host / 文件压根没读），写到终端，给
  `sdmc:/3ds/3dssh/config.ini.example` 的提示。
- `connect_and_open()` 的同等守卫也改成**写明话**（「No machine #N: M configured
  —— edit config.ini」），不留静默 return 的余地。
- **顺手把 boot 路径上剩下的两处静默出口也补了**（同一类缺陷，同一条排查线）：
  - `net_init()`（= `socInit`）失败 → `goto idle_loop`，**一个字都没写**。真机上它
    有模拟器永远不练的失败理由（无线开关关着、nwm 没起来），任何一个从外面看
    都跟"DSSH 启动卡住"一模一样 → 现在写 `Network unavailable: <socInit 码>` +
    「DSSH needs Wi-Fi — check the wireless switch」。
  - `if (!term || !r || !kbd || !kb || !mc) goto cleanup;` → **裸退出、白屏、不说是
    哪个子系统** → 现在在 `term` 可用时点名缺的那个（`terminal / renderer /
    keyboard / soft-keyboard / mascot`）。
  - 至此 boot 路径上**没有静默 `goto` 了**（剩下那个 `goto idle_loop` 是"开了
    picker"，picker 本身就是 UI，不算静默）。

**修后**（见上表 `bootnocfg`）"No SSH machine is configured." 等三条提示直接
上屏，**用户不再被静默抛在冰框下**。

**回归（`finalreg/t16.png`）**：正常旧 `config.ini` 直接到项目页，无变化。

### T60. 旧 Tailscale state 文件决定新构建的启动行为（P0，已修）

**症状**：用户任何时候在一台机器上**成功注册过 Tailscale**，写盘留下的
`sdmc:/3ds/3dssh/tailscale.state` 就成了「这台 3DS 永远会启动 Tailscale」的隐式
信号——无需 `config.ini` 里出现任何键。后果有两个：

- **冷启动卡 30 s+**：boot prologue 把 `ts3ds_up()` 放在 picker **之前**、在
  没有按键轮询的唯一线程上、又没有超时收紧（libts3ds 默认 30000 ms），拨号
  黑洞 IP 就直接冻住。
- **失败就 abandon startup**：`ts3ds_up()` 失败走 `goto idle_loop`，picker 与
  SSH connect 都跳过，**terminal 永远不会出 prompt**（见上表 `bootts/t6.png`）。

**根因**：`config_tailscale_should_start()`（`config.c:436-445` 旧版）：

```c
if (cfg->tailscale_auth_key[0]) return 1;       // 显式意图
if (!cfg->tailscale_state[0]) return 0;
FILE *state = fopen(cfg->tailscale_state, "rb"); // ← 用数据文件的存在当意图
if (!state) return 0;
fclose(state);
return 1;
```

「数据文件存在」被当成了「用户要 Tailscale」。

**修法（三件事，不是同一行）**：

1. **`config_tailscale_should_start()` 改语义**：删掉「state 文件存在就启动」
   这条。**意图**写在 `config.ini` 里：`tailscale_auth_key` 或新键
   `tailscale_autostart = 1`。`tailscale_autostart` 由 app **在成功注册后**
   自动写回（`config_save_tailscale_autostart()`）—— 节点的"重新上线"行为
   因此保留，但记录的是**意图**而不是数据文件的存在。
2. **bring-up 从 prologue 搬到 `connect_and_open()`**：picker / 单机器直连
   决策完成、`"connecting to X..."` 已经上屏之后再做 Tailscale 拨号。这样
   picker 永远在网络之前可达；单机器路径的等待**有标号**不再是冻屏。
3. **失败改为非致命**：`tailscale_bring_up()` 在 dial 失败时回 NULL，由
   `connect_and_open()` 走直连（`path_policy=auto` 本就允许直连），不再
   `goto idle_loop`。同时把超时收紧到 12000 ms（`DSSH_TAILSCALE_CONNECT_MS`，
   之前是 libts3ds 的 30000 ms 默认），并在成功注册后写 `tailscale_autostart = 1`。

**A/B 设备侧（关键）**：同一个 fixture `fixture-tailscale-boot-20260920`，
旧构建（shipped）见 `bootts/t6.png`（死终端）、新构建见 `newtskey/t12.png`
（项目页可达）—— Tailscale 报错**还在**，但 SSH 连上了。`newtskey` 和
`bootts` 的**唯一变量是构建**，不是 fixture。

**逆控设备侧**：`fixlegacy/t16.png`：旧 `config.ini` + 留有 `tailscale.state`，
**新构建无 Tailscale 启动动作** —— state 文件不再自动触发。这是 T60 在设备上
的直接证据（旧构建跑过同 fixture 是这函数的已知行为；代码 `config.c:436`
两行就是触发点）。

### T61. 配置文件没版本号，降级会静默吃掉别人的键（P1，已修）

**症状**：将来某个 `DSSH` 把 `config.ini` 加了新键、新的 `settings.ini` 加了新
段，旧构建拉回来用 → 读完，`settings_save()` / `config_rewrite_assignment()`
**整文件覆盖**，新键**整段被丢**。用户原本用 newer build 创建的项目、主题等
可能因为这次降级被擦掉，**而不会有任何提示**。

**根因**：两个文件都没"这是哪个版本写的"的字段，所以**写者无法判断"这张卡
是不是我的"**，一律按"我的"覆盖。

**修法**：

- `config.h`：新增 `#define DSSH_CONFIG_VERSION 2` / `DSSH_SETTINGS_VERSION 2`。
  `ssh_config_t` 加 `int file_version`，`dssh_settings_t` 加同样的字段。
- `config_load()` 解析 `config_version = N`，写进 `cfg.file_version`；
  `settings_load()` 解析 `settings_version = N`。
- `settings_save()` 开头加守卫：`st->file_version > DSSH_SETTINGS_VERSION`
  → return -1；写 `settings_version = 2` 由**常量**产出（不是 `st->file_version`）
  保证两者永不分歧。
- `config_rewrite_assignment()` 加守卫：扫**被写的那个文件**里的 `config_version`
  而不是 in-memory `cfg.file_version`，比静态全局更可靠（不依赖调用方先 load）。
  新增 `static int config_version_in(const char *buf)` 实现这个扫描。
- `config_file_is_newer()` 公开：main() 用它在横幅上画一行升级告示（见 T61 下
  的告示形态）。
- `config_save_selected()` / `config_save_machine_name()` /
  `config_save_tailscale_autostart()` 全部经过 `config_rewrite_assignment()`，
  自动获得守卫，不需要各自重复判断。

**降级告示**（T61 的可见部分）：

- 启动横幅：若 `config_file_is_newer(&g_cfg)` → 写一行
  `"config.ini is from a newer DSSH (format N, this build reads 2):
   loaded, but never rewritten."`，颜色用 `0x33`（黄）而不是红。
- 同样：`settings_save()` 检测到更新版本时，`connect_and_open()` 在写 banner
  之前会写 `"settings file is from a newer DSSH ... changes will not be saved"`。
- 旧/无版本文件**依然可写**（迁移就是"下次保存时升级格式"），只有
  **未来版本**的才被冻结。

### T62. 占位 host 被算作机器，无 host 的 config 假装有台机器（P1，已修）

**症状**：`config.ini` **存在**但从来没赋过 `host`（手写漏字、大小写不一致、
BOM 不知道、被 Word/CRLF 害了什么都不奇怪），旧代码把 `machines[0].host` 里
**默认值** `your-server.example.com` 当成机器 0，**去连**。结果是一个 DNS 失败，
**看起来像网络问题**而不是"你的 config 里没有 host"。

**根因**：`config_load()` 用 `if (cfg->machines[i].host[0]) count = i + 1;`
算 `machine_count`——默认值非空就被算进去。但这个占位从来不是"用户配的"，
是"你没配时该字段不至于 unset"。

**修法**：

- 在 `config_load()` 里加 `int host_from_file[DSSH_MACHINES_MAX] = {0};`，
  在 `host` 分支里 `host_from_file[idx] = 1`。
- 计数循环改成 `if (host_from_file[i] && cfg->machines[i].host[0]) count = i + 1;`
  —— **用户赋的、非空的**才计。
- 顺手把这段循环的注释里那个**错的**"contiguous"删了（§17 / T58 那条"host_N
  索引留洞 = 一台连不上的幽灵机器"曾经明确说过 contiguous 是错的）。
- "占位在 `machines[0].host`" 这件事保留（保持 `config_load` 的 defaults 形状
  不变），只是不再**被计数**。

**设备侧**（见上表 `fixnohost/t14.png`）："No SSH machine is configured." +
"config.ini was read, but it has no usable host — every host_N line is
missing or empty." —— 用户**立刻**知道是 config 问题，不是网络问题。

### T63. 降级保护 fail open —— 三套版本号解析规则互不一致（P1，已修）

**症状**：`config.ini` 写着 `config_version = 99999` 时，启动横幅画
"loaded, but never rewritten"，然后第一次连接**照样回写这张卡**。也就是说
T61 造的那道闸门，在最需要它的输入上不开。

**根因**：同一个"这文件是不是更新版本写的"，代码里有三个答案：

| 位置 | 取值规则 | 上界 | 后缀变体 |
|---|---|---|---|
| `config_load()` | 最后一条 | 无 | `config_version_2` **算** |
| `config_version_in()`（写者守卫） | 取 max | `<1000`，越界**清零** | 不算 |
| `settings_load()` | 最后一条，`(int)v` | 无 | 不算 |

三处都能和另一处分歧，且分歧方向一律是**放行**：

- `config_version = 99999` → 读者说"更新版"（横幅承诺只读），守卫把它**重置
  成 0**（`if (v > found) found = (v>0 && v<1000) ? v : 0;`），于是写者放行。
- `config_version = 3` 后面再来一条 `= 99999` → 同上，第二条把第一条抹掉。
- `config_version_2 = 99` → 读者经后缀拆分把它当成全局版本，横幅说只读；守卫
  按设计不认这条 → 放行。
- `tailscale_autostart_1 = 1` / `selected_machine_3 = 0` → 同族：后缀拆分把
  全局键挪进了带洞的槽位，实测 autostart 被置 1。
- `settings_version = 4294967298` → `(int)` 折回 2，**正好等于本构建的版本**，
  守卫关闭；而 `settings_save()` 是按字段表整表重写，于是把新版才认的键真丢掉
  了 —— 这一条是真的数据丢失，不是"提示不准"。

**修法**：`parse_version_value()` 一个函数三处共用 —— 只认数字、可选引号
（加载器 unquote 过、守卫扫描没有）、超过 `DSSH_VERSION_CAP` 一律**夹住**而不
是回绕、重复行取 max。`config_load()` 里三个全局键（`config_version` /
`tailscale_autostart` / `selected_machine`）连同四个 `tailscale_*` 一律加
`!has_suffix` 守卫，与写者扫描的边界规则对齐。

**证据**：改前 `probe2` 四行里三行 `save_rc=0`（该拒的没拒），改后四行全部

个答案**，这样以后只改一边就会红。`test-config` 264 → 307 条。

### T64. `config_version` 只有读者、没有写者（P2，已修）

**症状**：全仓库没有任何代码往 `config.ini` 里写版本行，所以
`config.h` 的"legacy 文件会在下次保存时原地升级"这句对 `config.ini` **不成立**
（对 `settings.ini` 成立，那边是 `settings_save()` 用常量写出来的）。一张卡会
永远停在 version 0，而 0 的含义正是"不认识"。

**修法**：`config_rewrite_assignment()` 在守卫之后补一段：文件不带版本行就顺手
补一行 `config_version = 2`（从常量产出）。于是 T63 的机制第一次真正闭环 ——
本构建写的文件，未来构建能认出来。

**证据**：实测 `probe` 的 D 段，保存后文件末尾出现 `config_version = 2`。测试
放在"legacy 裸 `name` 键"那一组（故意留一个 legacy fixture），断言精确字节：
一次保存加**且只加**一行，第二次保存不再加。

### T65. 两份 README 还在讲 T60 删掉的那条规则（P2，已修）

`README.md:301` 与 `README.zh.md:273` 都写着"没有 auth key 时只要 state 文件
存在也会自动启动"——正是 T60 刻意移除的行为，而且 08c11c9 已经为
`config.ini.example` 里**同一句话**做过一次修正，主文档漏了。`README.md` /
`README.zh.md` 里 `tailscale_autostart` 与 `config_version` 出现次数为 0。

**修法**：两段重写（启动条件改成"auth key 或 `tailscale_autostart = 1`，除此
之外都不启动"，并说明**怎么关**——这是 T73 之外用户唯一能取消自动拉起的入口）；
字段表补 `tailscale_autostart` / `config_version` 两行；新增一段版本号机制说明；
多机器小节补"编号必须连续"这条新规则（与 T66 对齐）。`config.ini.example` 另
加 `config_version` 段，并修掉 `ui_language = 0 # 0=Chinese 1=English` 的漂移
（实际 0..5，d491148 只修了 `config.h`）。

### T66. `host_N` 留洞的幽灵机器 —— T58 挂着、T62 明确"本轮不修"，这轮修了（P2，已修）

**症状**：`host_0` + `host_2`（无 `host_1`）算 3 台机器，picker 把中间那个空槽
当一行卖给你，点下去是一个空主机名的 DNS 失败 —— 看起来就是网络问题。T62 把
"一台都没有"这条路堵了，却没堵"有一台是洞"，而它俩的症状一模一样。

**修法取舍**：三个方案里选了最小的一个。
- ~~picker 过滤空槽~~：要动 `machine_ui.c` 的 row↔index 映射（`open`/`tick`/
  两处 `draw` 都用 `n = machine_count`），还要让 `config_save_machine_name()`
  收到映射后的槽位号，改动面覆盖一整套 UI 测试。
- ~~把有 host 的槽位压成 dense 数组~~：内存 index 不再等于文件里的 `host_N`，
  改名会写错机器 —— 制造一个新 bug。
- ✅ **`machine_count` 只数连续前缀**（第一个空槽即停），于是"count 可以当
  loop bound 用"这个前提第一次成立；被落下的机器数记进新字段
  `machines_after_gap`，启动横幅说"有 N 台在洞后面，编号补齐才进得来"。

代价：第三台机器**看不见**了 —— 所以那条横幅是这条修法成立的前提，不是装饰。

**证据**：`probe` 的 C 段从 `machine_count=3 slot1 host=''` 变成
`machine_count=1`；测试改成断 `count==1 && machines_after_gap==1`，另加"两个
洞数到 2"和"连续文件报 0"两组，免得提示误伤。

### T67. auth key 被抹掉后，本会话**静默**放弃 Tailscale（P2，已修）

**症状**：`tailscale_bring_up()` 在拨号之后无条件
`memset(g_cfg.tailscale_auth_key, …)`（正确：用完就不该留在 RAM 里）。
但 `config_tailscale_should_start()` 是**读那个字段**判断要不要拉 Tailscale
的，于是一张"只有 auth key、还没有 autostart"的卡第一次拨号失败之后，
`should_start()` 从此回答 0 —— 同一会话里每次重连都不再试 Tailscale，屏幕上
没有任何一句话说明这件事，只能重启。

**根因**：把"用户要不要 Tailscale"这个**意图**建立在一个**会被安全清理掉的凭
据**上。上一轮把 bring-up 从 boot 挪进 `connect_and_open()`（正确）之后，这条
路径才从"每次启动一次"变成"每次连接都问一遍"，暴露面被放大。

**修法**：`g_ts_intent` 首次问、之后记住（-1 未决 / 0 / 1）。失败仍然可以在用
户主动重连时重试 —— 那是重试的本分；变的是**不再因为凭据被清掉而改主意**。
`config.h` 里 `config_tailscale_should_start()` 的注释点明"它读的是调用方有权
销毁的数据，所以要采一次记住"，防止下一个调用点再踩。

### T68. `connect_and_open()` 对 `idx < 0` 仍然一个字都不写（P3，已修）

上一轮的立论是"boot 路径不许有静默死路"，但守卫写成
`if (term && idx >= g_cfg.machine_count)` —— 负数（选择页什么都没选）落进来
照样静默 return。现在两种情况各说一句：越界指向 `config.ini`，负数指向 UI
（"按 SELECT 重新选"）。顺带删掉 157a07e 那句
`term ? "" : "terminal "`：外层 `if (term)` 已经保证非空，第一个 `%s` 永远是
空串。

### T69. `net_init` 提示的缓冲区差 1 字节（P3，已修）

`char line[200]` 配 `%.110s`：编译器的
`-Wformat-truncation` 算出来是 **91–201 → 200**。真被截断时，掉的是行尾的
`\r\n`，更坏是第二行那个 `\x1b[0m` —— 于是"说明网络不可用"的这句话自己把
之后的终端染成暗红。改成 224。同一条注释里说明为什么最少也有 91 字节
（两条转义 + 中文破折号各 3 字节）。

### T70. `mascot_mode` 的值域停在 0..4，牛来和刀盾狗存成螃蟹（P1，已修）

`settings_fields[]` 写 `0, 4`，而设置页有 7 项（`nopts = 7`，0=关 +
`MASCOT_SPECIES_COUNT = 6` 个物种），`softkb_apply_settings` 与 `config.h`
都按 0..6 讲。后果：**选 5 或 6 → 立刻生效 → 保存被 `field_sanitize` 夹回 1 →
下次开机是螃蟹**，中间没有任何提示。

这条最扎心的地方在于 `config.c:648-657` 那段注释，正是讲"值域只能有一个来源，
以前 `bottom_info_mode` 漂移过一次"，而它自己下面第三行就漂着。

**修法**：新增 `DSSH_MASCOT_MODE_MAX`（`config.h`，带整段来历），
`settings_fields[]` 与 `softkb.c` 的那处 `<= 6` 都改用它；
`mascot.c` 里 `_Static_assert(MASCOT_SPECIES_COUNT == DSSH_MASCOT_MODE_MAX)`
把两边钉死 —— `config.c` 不该依赖渲染器的头文件，所以断言从 mascot 这一侧做。
测试遍历 0..6 存读一圈，另加"手写 6 不被夹"和"手写 99 仍然回落"。

### T71. 项目卡里打一个 `#`，这张卡重启就没了（P1，已修）

`settings_load()` 对**每一行**先 `strip_comment()`，而 `field_escape()` 只转义
`\` 和 `|`。于是 `Fix #12` 读回来是 `Fix `，字段数不再等于 9，
`parse_project_row()` 返回 0，而那条分支的处理是 **memset 掉这个槽**；下一次
保存把 `[projects]` 整段按内存里的样子写回去 —— 卡真的没了。软键盘上有 `#`
键，路径/参数/命令/备注四个字段都会撞。

同样的坑在机器名那条路上是**已经认过并修过的**（`config_save_machine_name()`
给含 `#` 的名字加引号，注释就写着"否则 strip_comment 会把它截断"），只是项目
行格式没有引号可加。

**修法**：`[projects]` 段内不做 `strip_comment`。副作用检查过：段内一条手写的
`# project_0 = …` 现在既不是注释也不是可识别的键，落进"不认识的键忽略掉"，
比"覆盖一张真卡"安全。测试断言 name/path/args/cmd/note 五处的 `#` 全部原样回
来、后一张卡不丢，另断一条注释行不多不少。

### T72. `settings_save()` 先截断再写，写坏了就把文件毁了（P1，已修）

`fopen(path, "w")` + 缓冲 `fprintf` + 只在末尾 `fclose` 检查。卡满时每个
`fprintf` 都静默失败，留下 0 字节或半截文件，`-1` 是**事后**才返回的。而这个
文件的全部内容就是项目卡，且 `project_run()` 每次启动都保存一次 ——
一次 ENOSPC 就能清掉用户所有卡。

讽刺点：`config_rewrite_assignment()` 的注释里就写着这条教训（"a card that
fills up mid-write must not eat the credentials"，T47 那轮加的），但这一半没人
补。

**修法**：拆出 `settings_emit()`，`settings_save()` 走 tmp + rename +
原地回退，**并沿用 config.ini 的只读探测**（`fopen("a")`）—— 否则 rename 会
绕过用户刻意设成只读的 `settings.ini`。测试断三件事：保存后不留 `.tmp`、
只读文件被拒且内容不变、被拒时不产生半截文件。

### T73. 含全部明文凭据的 `.tmp` 副本没有清理路径（P2，已修）

`config.ini.tmp` 只在"rename 失败"这条进程内分支被删。写入与 rename 之间断电
/ 拔卡，卡上就留下一份完整明文副本：每台机器的 passphrase、
`macos_keychain_password_N`、`tailscale_auth_key` —— 包括用户**后来从
`config.ini` 里删掉**的那些。全仓库没有任何地方 unlink 它，而 boot 时的
`clear_secret()` 只管 RAM。

**修法**：`discard_temp_copy()`，在 `config_load()` 与 `settings_load()` 开头
各调一次（它们本来就要打开同一个路径）。测试手写一个 `.tmp` 再 load，断它消
失。

### T74. 语音转写回传的字节原样打进 PTY，回车不滤（P1，已修）

`voice.c` 的打字机路径把 `reply_buf` 里每个字节 `ssh_write` 进**远端 shell**。
所以转写结果里出现一个 `\r`，就是替用户提交了一条命令：`ls -la\rrm -rf ~\r`
一次"转写"就能执行。和文档里挂着的那条"host key 不验证"不是一个量级 ——
那条只影响**显示**，这条影响**执行**，而且是 app 里唯一一条不经用户瞄准就到达
shell 的输入通路。

**修法**：`enter_typing()` 入口（IME 唯一的闸门，`flush_typing()` 的中断路径
也走它）剥掉除 `\t` 外的所有 C0 和 DEL；剥空了就安静回 IDLE（同"非语音被门拒
掉"那条既有语义）。`≥0x80` 全部保留，UTF-8 多字节不受影响。
**不是**内容审查：`;` 和 `&&` 照旧能进来 —— 不带回车的文本正是这个功能的形
态。`--ask` 那条路走 modal、不经过这里，未改。

### T75. `dssh_project_command()` 返回的是"本应写多少"（P3，已修）

`snprintf` 的返回值是未截断时长；六个分支原样返回，而 `copy_clamped()` 那条返
回的是实际写入数 —— 一个函数两种契约。调用方
`project_queue_or_send()` 拿它当索引用：`line[n++] = '\n'; line[n] = 0;`。
今天差 25 字节不炸（`line[352]`，最坏组合 325），但没有任何东西阻止
`DSSH_PROJECT_ARGS_MAX` 抬一格就变成栈溢出。头注释"Returns the length"本身就是
歧义来源。

**修法**：`snapped()` 夹到 `out_sz - 1`，六个分支都包；头文件把契约写成
"bytes NOW IN `out`，从不超过 `out_sz - 1`，**这**才是调用方在边界内存活的依
据"。

### 诚实边界

- **没有上真机**。模拟器（Azahar + Vulkan）过了一遍，见上一节那张表；真机
  （实体 3DS + 真 Wi-Fi）没有。二者差别最要紧的是 T67：`socInit` / nwm 的
  行为、以及一次真实拨号失败之后的重连，模拟器给不出可信答案。T74 的转写过滤
  两头都没测（要改 shim 回包内容）。
- **T74 的威胁模型是"服务端/中继不可信"**，不是"用户自己打错字"。修法只压住
  了控制字符这一类；如果哪天转写需要输出带换行的多行文本，这个过滤要重新设计
  （并且要重新想清楚"打进 shell"这件事的边界在哪）。
- **T66 选择了"看不见"而不是"看得见但连不上"**，代价是第三台机器需要用户自己
  按提示去补编号。`machines_after_gap` 只报数量、不报具体哪些下标，因为一条
  25 字节的横幅放不下；真要精确到"host_1 空"，得把下标也带出来。
- **T64 让 legacy 卡在第一次连接时多写一次 `config.ini`**（补版本行）。这是
  一次性代价，换来"本构建写的文件未来的构建认得"。写仍走 tmp+rename，失败不
  影响连接。
- **`settings_version` 溢出这条（T63 最后一种）是构造出来的**，不是实测哪张卡
  上有 —— 现实里更可能是某个未来版本真写了个大数字。修它的理由是"另一个方向
  会真丢数据"，不是"有人撞到了"。

### 修掉的三件发布阻塞

1. **主机密钥不验证从没写进用户文档**。第八节把它列为【严重】，而 README 的
   Known limitations 列了明文私钥、列了只认 RSA PEM，独独没有它。双语各补一条，
   并说清真正的代价：假服务器可以自己印一行解锁提示，于是
   `macos_keychain_password` 那条路把登录口令送给中间人（私钥不出 SD 卡，
   丢的是会话保密性，外加屏幕上显示什么由他决定）。服务端那一节的 ⚠️ 块加了指路。
2. **装完看不出是哪一版**。`app.rsf` 没有版本字段、二进制里没有版本串，用户报
   bug 无法对齐到提交。现在 Makefile 从 `git describe` 派生 `DSSH_VERSION`，生成
   `build/version.h`，开机画面多一行 `DSSH <ver>`，CIA 的 SMDH 长描述同样带上。
   做成 `main.o` 的依赖而不是 `-D`：后者会让 `make DSSH_VERSION=v1.4.0 cia` 出一个
   SMDH 写 v1.4.0、开机画面仍写旧版本的包 —— 正是 `$(CIA_TARGET)` 那条注释防的
   stale-ELF 坑。
3. **README 的演示视频是 404**。`releases/latest/download/demo.mp4` 从 v1.3.0 起
   断的：v1.0/v1.1/v1.2 三个 release 都传了 `demo.mp4`，v1.3.0 漏传，"latest"
   这条链接因此指向空。链接写法不用改，改的是发布动作 —— 每个 release 都得带这个
   asset，见 `docs/release-checklist.md`。

### 评审回补（2026-10-14，对本次版本戳改动的事后评审）

评审把版本戳端到端实跑了一遍（干净全量重建、`make DSSH_VERSION=… cia` 贯通、
20 套门禁、SMDH 解码），改了两处 Makefile、更正了本节两处数字。

- **本节初稿那句"HEAD 里没有 T74"不成立**：T63–T75 就在本节提交的 64 秒前落成
  `74df906`，HEAD 的 `voice.c:213` 有 `strip_reply_control_bytes`。风险描述本身
  没错，但落点是 **origin/main**（公开仓库还停在 08-16），不是 HEAD。照原句读会
  以为要从 HEAD 重做这个过滤。
- **`.PHONY: FORCE` 漏在编译上下文**（Makefile 的 else 分支）。顶层分支声明了，
  而决定二进制版本号的是 sub-make 这一侧。复现：`build/` 里放一个 mtime 早于
  `version.h` 的 `FORCE` 文件，`make DSSH_VERSION=… all` 直接 "Nothing to be
  done"，头文件冻结在旧串 —— 正是这次改动要防的那类错，且 `make clean` 的删除
  清单匹配不到它，一旦产生就永久生效。已在 else 分支补 `.PHONY: FORCE`。
- **`export DSSH_VERSION ?= $(shell git describe …)` 是递归赋值**，每次展开都重跑
  `git describe`；一次 `make cia` 展开两遍（导出给 sub-make 一次、SMDH 长描述一次），
  中途有提交或 `-dirty` 翻转就会让二进制与 SMDH 各写一个串。改成
  `ifeq ($(origin DSSH_VERSION),undefined)` + `:=`，展开一次，命令行与继承环境的
  覆盖语义不变。
- **实测留档**：`make clean && make -j4 all` 全树只剩 `main.c:1006` 那条既有
  `-Wformat-truncation`；随后 `make -j4 all` 完全 no-op（`main.o`、`version.h`
  mtime 未动，`cmp` 守卫按注释所述工作）；`make DSSH_VERSION=REVIEW-TEST-123 cia`
  后该串同时出现在 `main.o`、`3dssh.elf` 和 SMDH 十六个语言槽的长描述里；
  20 个 `make test-*` 全绿；没有任何宿主机测试编译 `main.c`，所以
  `#include "version.h"` 不会拖累门禁。
- **`strings DSSH.cia` 查不到开机版本号**：makerom 把 content 段加密了，只有
  SMDH 那段是明文（实测明文偏移 1421056）。别据此判定版本戳没进包 —— 要看
  `build/version.h`、`3dssh.elf`，或装机看开机画面。
